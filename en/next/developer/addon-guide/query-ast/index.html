    Query AST: saving a search and running it later

    Status: implemented. A saved search, a dashboard tile, an export or an agent tool describes its query as one JSON document, the query AST. Any code can parse it, check its shape, store its canonical text, and later run it as whoever is running it, with that person’s rights. The decision is ADR 0045, the behaviour is docs/specs/orm/query-ast.md (SPEC-QAST), the design is docs/design/m3-qast.md.

    Odoo keeps saved filters as three Python-literal text columns and applies them with the rights of whoever opens them; nothing checks them until they run, and nothing bounds them. The AST keeps the second part (it always runs as the person who runs it) and fixes the rest: a versioned format, one canonical form, strict parsing, limits, a check against the current registry at every run.

    The document

    Section titled “The document”

    A document is a JSON object with a version, a kind (search_read or read_group), a model, a domain, an optional context, an order and a page. Every object has a closed set of keys: an unknown key is an error, never ignored.

    • limit is required: 1 to 2,000 rows for search_read, 1 to 10,000 groups for read_group. A larger value is an error, not a cap. offset (default 0) is at most 1,000,000.
    • fields is a non-empty list: there is no “all fields”, because “all” changes meaning when the registry changes.
    • domain is Odoo’s list syntax. A value can be a principal parameter, {"param": "uid"}, which stands for the person who runs the query: uid, company_id, company_ids, today or now. The document never holds a user id or a company of its own.
    • context takes one key, active_test (a boolean). lang, tz and allowed_company_ids come from the running environment, as they do for a live call; any other key is refused.
    • In a read_group document, order and having name a group-by (invoice_date:month) or an aggregate (__count, amount_total:sum) declared in the same document. array_agg, array_agg_distinct and recordset aggregates (unbounded output per group) are refused.

    Build it in Rust

    Section titled “Build it in Rust”

    The builder’s domain(...) takes an erp_sdk::query::Json tree of the list syntax. A builder collects the same document the parser reads and runs the same validation in build, so a built AST and a parsed one accept and refuse the same things. A mistake is a QueryAstError with the path of the element: query AST $.model: invalid model name 'Bad Model': ....

    Parse, store, compare

    Section titled “Parse, store, compare”

    Two documents that differ only in key order or in absent keys versus their defaults are the same query and have the same canonical bytes. Hash the canonical bytes if you need an identity. Store them as text, not jsonb: jsonb rewrites numbers and drops duplicate keys.

    QueryAst::parse takes bytes. A layer that already holds a parsed JSON tree (erp_fields::json::parse) passes it to QueryAst::from_json. Paging gives a new validated query: ast.with_page(limit, offset, &limits).

    Section titled “Limits”

    Run it

    Section titled “Run it”

    erp_sdk::query::run(tx, &env, &ast) checks the query against the transaction’s registry and the environment’s access, then runs it through Records::search_read or Records::read_group: the same statement, the same method chain, the same errors as the live call. check does the checks and fetches nothing.

    • No superuser mode. check and run refuse an environment in superuser mode (sudo(), the System principal) with an Access error: a favourite saved by anyone must not read every record. Audited elevated replay is planned.
    • The environment decides everything. The document carries no user. A query saved by an administrator and run by a clerk uses the clerk’s model access, record rules, field groups and company scope; {"param": "uid"} is the clerk’s id. Nothing is remembered between runs: no compiled statement, no “this query was valid” flag.
    • A field the person cannot read, or that no longer exists, fails the run with an error that names it (Access or Validation). The query never runs with the field left out: a dropped fields entry would change what a report means, a dropped domain condition would broaden it.
    • truncated is true when more rows or groups matched than the query’s limit. The ORM fetches limit + 1 in the same statement to know.
    • check follows the planning half of the code run uses. For plain conditions it sends no data statement; child_of / parent_of and access conditions are resolved through the database, so check may send statements for them. It does not call #[method(override)] implementations of _read_group; run does.
    • Stable pages. A grouped run adds the group-bys your order does not name, ascending, after your terms, so groups tied on an aggregate keep one order and offset paging does not repeat or skip groups.
    • Time. A query is bounded in size, not in running time. Run it under the host’s statement_timeout (the HTTP server will set one per request); 2,000 rows of heavy x2many or computed fields cost what they cost.

    Errors

    Section titled “Errors”
    ErrorKindWhen
    QueryAstErrorValidationthe document is refused: path and reason (query AST $.limit: limit is 2001; at most 2000 allowed)
    unknown or abstract model, unknown field, bad granularityValidationthe registry no longer fits the document
    no read access to the model, an unreadable fieldAccessthe running principal’s rights

    erp_fields::Error::from(query_ast_error) gives the Validation error with the original as its source, so ? works in functions that return the shared Result.

    What is not here

    Section titled “What is not here”

    The storage of saved queries and their UI, turning a natural-language question into a document, the RPC method and tool that run a document, the JSON Schema of the format and scheduled runs are all planned.
