    Stock quant engine

    A stock balance (stock.quant) holds the on-hand and reserved quantity of one key: company, product, exact location, and optionally lot, package and owner. Balances are a projection of the stock ledger (ADR 0079, ADR 0139). Only one path writes them: erp_addon_stock::apply_quant_changes. Generic ORM writes of a balance are refused by name.

    The stock transitions that use the engine (move validation, inventory application) are later slices. Until they exist, nothing user-visible changes a balance.

    API

    Section titled “API”

    All items are re-exported at the crate root of erp-addon-stock.

    ItemWhat it does
    QuantKeyThe six key parts. The company is the ledger line’s company, never derived from the location. Build it with QuantKey::new(company, product, location) and .lot_id(..), .package_id(..), .owner_id(..).
    QuantChangeA signed on-hand delta, a signed reserved delta and the incoming date the stock carries: QuantChange::new(key, quantity, reserved), .in_date(..).
    apply_quant_changes(tx, &[QuantChange])Applies a batch in the caller’s transaction and returns the new balances, one per distinct stored key, in lock order.
    QuantFilterWhich balances a read covers: broad (the location and its descendants) or strict (exact key parts): QuantFilter::new(company, product, location), then .strict(..), .tracked(..) and the part setters.
    gather_quants(tx, &QuantFilter)The matching balances, lot-bearing ones first, then by id. One query.
    available_quantity(tx, &QuantFilter, allow_negative)Free quantity of the filter. One query.
    QuantErrorEvery refusal, with its message and error kind.

    apply_quant_changes needs a REPEATABLE READ transaction, the ORM default. Use the native run_quant_unit entry below for a complete stock unit, including its probe and document changes. The ordinary Orm::run retries serialization failures but does not retry stock lock timeouts.

    Before it writes, a batch is checked as a whole. It is refused with nothing changed when:

    • a change has neither quantity nor reserved quantity;
    • a delta has more decimal digits than the Product Unit precision;
    • the product is not storable, the location is a view, or the lot belongs to another product;
    • the product, location, lot or owner belongs to another company than the key (a location of a parent company is accepted);
    • the company, product, location, lot, package or owner does not exist (a defect of the caller);
    • a release would take the reserved counter below zero. This is a defect of the caller and is reported, never clamped.

    The engine reads by SQL. Pending ORM writes of the transaction (a location usage written just before, a storable flag) are flushed before the checks, so the batch is checked against them. A key another transaction deleted after this one started is answered as a serialization failure (40001), which Orm::run retries.

    Changes at supplier, customer, inventory adjustment and production locations are accepted and store nothing: those balances live in the ledger only. A key whose quantity and reservation reach zero is deleted, unless it has a counted quantity or an assigned user.

    The incoming date of a key is the earliest of its own date (while it holds positive stock) and the dates its changes carry. With neither, it is the time of the call.

    Native stock unit runner

    Section titled “Native stock unit runner”

    run_quant_unit(orm, unit, work) runs a repeatable async callback in a fresh transaction on every eligible retry. Build QuantUnit::new(principal, operation_identity, product_label) with a label that the caller is authorized to see, and use .context(context) when needed. The entry takes its policy snapshot once and keeps the same identity and inputs across attempts.

    The callback includes the availability probe, document changes and quant changes. It may be called again: keep external effects outside it and register post-commit effects with tx.after_commit. Do not commit manually. The entry owns the whole transaction and refuses a surrounding ORM or RPC unit before reading policy. It is a native entry point, not an RPC method.

    Serialization failures and deadlocks retry the entire callback. A lock timeout retries only when the ORM classified it as such; a NOWAIT refusal does not. Exhaustion returns QuantRetryExhausted, with a Lock error kind, the product label and actual attempt count. Access, validation and programming refusals are terminal. An uncertain commit result is terminal: inspect the operation’s durable idempotency state before retrying it. Operation identity supplies correlation, not durable deduplication; the caller owns that protocol.

    The engine’s apply_quant_changes entry still borrows a transaction and never retries or commits on its own. Negative-stock policy changes use their separate policy-unit contract.

    Lock order

    Section titled “Lock order”

    The engine nets the changes of one call per key. It then sorts the keys ascending over (company, product, location, lot, package, owner), with an absent part after every present one (PostgreSQL’s ASC NULLS LAST). It locks them in that order in one statement, inserting a zero row for a key that does not exist yet. Two calls over overlapping keys therefore never wait on each other in opposite orders.

    The order holds across calls only under one rule: one engine call per unit of work, or later calls only with keys above the highest key the transaction already holds. Collect the changes of a unit of work and pass them in one call. The engine keeps the keys each transaction locked; a later call that names a lower key it does not hold yet is refused before any lock, as a Programming error naming both keys. A key the transaction already holds may come again in any order. A key locked inside a savepoint that was rolled back is no longer held, because the rollback released its row lock; the engine notices the rollback and treats such a key as new. Count-state writes through the generic write lock in row order; make them before the engine call or in their own unit of work.

    Quant keys come third in the lock hierarchy of ADR 0079 D4.1. A caller locks its picking, move and policy rows before it calls the engine, and cost keys after.

    A broad filter with a lot also counts stock without a lot. A strict tracked filter with a lot does not. The product’s tracking mode is a field added by the lot work (planned); until then the caller states it in the filter.

    Access

    Section titled “Access”

    The engine checks no model access or record rule, as an internal service. The transition that calls it has already checked access on its own documents. The engine is never an RPC method.

    On stock.quant:

    • create is refused, after the model access check (so a user without access still gets the access refusal);
    • write of a key part, quantity, reserved_quantity or in_date is refused, naming the field’s label; the counted quantity and the assigned user stay writable;
    • copy is refused, after the create access check;
    • the generic upsert by the declared key is refused, after the create and write access checks (it would run no create or write override);
    • unlink runs the model access check, then refuses a quant with an on-hand or reserved quantity for every caller, the superuser too. Deleting a zero quant requires the caller’s unlink access and record rules to allow it. The engine deletes its own zero keys.

    These refusals are user errors whose message says that balances change only through stock moves and inventory adjustments; the client’s New and Duplicate buttons can reach them.

    On stock.move and stock.move.line, the done time, and on lines also the membership and the correction counter, are written only by the stock engine: a create or write that names one of them is refused for every caller, after the model access check, with a user error naming the field’s label. Correction rows (stock.move.line.correction) and serial positions (stock.serial.position) are read only for stock users and managers; only the engine writes them.

    available_quantity is a non-stored field: on hand minus reserved, signed.

    Location guards

    Section titled “Location guards”

    A location write is refused when:

    • it changes the company of a location (archive it and create a new one instead);
    • it makes a location holding any balance a view;
    • it changes the usage of a location holding any non-zero on-hand or reserved quantity. The reference blocks only positive stock; here a negative or reserved-only balance blocks too, because a balance at a virtual usage is never stored and would stay frozen there;
    • it archives a location whose internal locations (itself or below) hold stock.

    The checks also catch values that convert to a change: an active value other than true (null or 0 from RPC, an empty or integer cell from Rust) is checked as an archive, and a usage value that is not a usage name is checked as a usage change. Pending ORM writes (a child moved to another parent just before) are flushed before the checks read.

    Concurrent stock changes. The engine takes a share lock on the locations of its keys. A location guard locks the locations it decides on (for an archive, every location below too) without waiting:

    • while a stock change at those locations is still open, the guard fails as a serialization failure and Orm::run retries it; once the change committed, the retry sees its balance;
    • a stock change that starts after the guard waits for the guard’s transaction, is then retried, and sees the new usage or archive.

    The tracking check locks the product rows in the same way, so an open insert of a lot, line or quant of the product retries it.

    Not covered yet: a stock change that committed after the guard’s transaction began and before the guard’s lock. The guard’s snapshot does not show it and no lock is left to meet, so the guard decides without it. Closing that needs the rule as a database constraint that is checked across snapshots.

    Settings

    Section titled “Settings”

    The native unit’s limits are declared technical system parameters of stock (ADR 0227), in Technical, System Parameters, not on the Settings page. Only system administrators read and change them there; the unit reads them itself (erp_sdk::params::get_int, elevated), so every caller of a stock unit has them applied. Each new invocation reads committed policy; a save does not extend an invocation already in progress. A stored text outside its declaration fails the invocation with Stored parameter <key> is invalid. before any work. Negative stock is allowed. The switch that forbids it per location is the location policy’s forbid_negative field; setting it is refused until a later quant slice enforces it. The decimal precision is the Product Unit precision (Settings, Technical, Decimal Accuracy).

    Every key below begins with stock.quant_. Zero is refused, not treated as unlimited; an empty or deleted row means the default.

    Key suffixDefaultAllowed range
    lock_timeout_ms1000 ms10–10000 ms
    max_attempts51–5
    retry_base_ms50 ms1–2000 ms
    retry_cap_ms2000 ms1–10000 ms
    idle_transaction_timeout_ms60000 ms1000–600000 ms
    tcp_keepalives_idle_s30 s1–300 s
    tcp_keepalives_interval_s10 s1–60 s
    tcp_keepalives_count31–10

    The retry base cannot exceed its cap (parameter group stock.quant_retry_backoff). The lock timeout must be below the transaction’s effective statement limit; incompatible values refuse the invocation before business work. Idle-session and TCP keepalive values apply locally to each transaction. Defaults are operational choices; performance calibration is deferred.

    Before stock 1.5 these keys were global Settings values. The 1.5 upgrade moves each stored value to the parameter of the same key (ADR 0227 §7): the Settings revision does not change, a parameter row that already held another text is replaced by the Settings value and audited with actor migration:stock@1.5, and a stored value outside its range stops the upgrade naming the key. The old rows stay in place, unread, for one release.

    Not yet available

    Section titled “Not yet available”

    Later quant slices, not yet on the board, add:

    • forbidding negative stock per location;
    • serial positions and the one-serial-per-location rule, after the lot work (planned);
    • compensation of lot-less negative stock when lots arrive;
    • quant display names, search and grouped reads;
    • relocating or repacking balances.

    Removal strategies, counted inventory and the quant list views of the web client are planned.
