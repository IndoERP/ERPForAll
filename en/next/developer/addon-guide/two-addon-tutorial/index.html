    Writing and extending addons: a two-addon tutorial

    Status: verified against the integration suite crates/erp-test-models/tests/two_addon_lifecycle.rs. Implements: ADR 0001 (addon mechanism), ADR 0005 (workspace and crate map), ADR 0009 (addon platform runtime).

    This tutorial walks through building, extending, installing, upgrading, and uninstalling two native ERPForAll addons:

    1. test_addon_a (Base Addon): Declares a new model test_addon.book, provides XML seed records, defines form and list views, and implements a custom method describe().
    2. test_addon_b (Extension Addon): Declares a dependency on test_addon_a, extends test_addon.book with new fields (isbn, rating), overrides describe() using Super chaining, and injects the new fields into the base form view via XPath.

    Step 5: Uninstalling and dependency constraints

    Section titled “Step 5: Uninstalling and dependency constraints”

    Dependency refusal check

    Section titled “Dependency refusal check”

    Uninstalling test_addon_a while test_addon_b is installed also uninstalls test_addon_b, as in Odoo: a live run cascades to the installed dependents and reports them. To see the effect first, use --dry-run, which plans without database state and refuses when an available addon depends on the one you named:

    Clean uninstallation order

    Section titled “Clean uninstallation order”

    To remove the functionality cleanly:

    1. Uninstall the dependent extension first:

      • Extended columns isbn and rating are safely dropped from test_addon_book.
      • The inherited view patch view_book_form_inherit is deleted, restoring the original form view.
      • ir_model_data rows for test_addon_b are purged.

    2. Uninstall the base module:

      • The table test_addon_book is dropped.
      • The base views, actions, menus, and external ID entries are purged from the database.
      • Module state in ir_module_module transitions to uninstalled.

    Key takeaways and best practices

    Section titled “Key takeaways and best practices”
    • One transaction per operation: an install, upgrade or uninstall is one PostgreSQL transaction (ADR 0009 §2); when anything fails, nothing of the operation is kept. See modules.
    • Strongly Typed Extension: Extensions use Rust’s type system with #[extend(Model)] and explicit Super chaining instead of loose string dispatch.
    • Fail loudly: an unknown module is refused with an error that names it.
