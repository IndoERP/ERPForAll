    Odoo compatibility

    How concepts from Odoo Community and Enterprise correspond to ERPForAll’s native Rust crates and data-only addons, and where ERPForAll behaves differently.

    ERPForAll is an ERP framework rebuilt in Rust, modeled on Odoo: a faster, leaner ORM, a clean and reactive web client, and modular addons that declare and extend models, views, menus, actions, security, and UI. While the mental model closely mirrors Odoo’s architectural concepts, ERPForAll replaces dynamic Python runtime patching with Rust’s compile-time type safety, memory safety, explicit contracts, and strict “fail loudly” error handling.

    2. Key Differences in Detail

    Section titled “2. Key Differences in Detail”

    Manifest and Addon Declaration

    Section titled “Manifest and Addon Declaration”

    In Odoo, an addon is identified by __manifest__.py. In ERPForAll:

    • Native Addon: A Rust crate with a Cargo.toml and a manifest.toml. The crate root calls erp_sdk::addon!(name = "sale_stock", depends = ["sale", "stock"]); as documented in models.md (“Declaring an addon”). Notice that base is always an implicit dependency in erp_sdk::addon!, so depends lists only explicit non-base addon dependencies. In manifest.toml, depends = ["base", "other_addon"].
    • Data-Only Addon: A plain directory containing manifest.toml, models/*.toml, and data files (XML/CSV) without Rust compilation (see cross-addon-extension.md).

    Models and Extension

    Section titled “Models and Extension”

    In Odoo, models.Model classes are dynamically instantiated and monkey-patched at runtime via _inherit. In ERPForAll:

    • A new model is defined with #[model(name = "tech.name", description = "Label")] pub struct ModelName;.
    • Extending an existing model from another addon is defined in the extending crate using #[extend(ParentModel)] pub struct ExtensionStruct;.
    • The Rust struct acts as a compile-time declaration tag. Record operations use RecordSet<ModelName>, and fields are accessed via generated typed associated constants (such as Book::NAME or BookPages::PAGES).

    Security and Access Control

    Section titled “Security and Access Control”

    Odoo historically splits access into ir.model.access.csv (table-level CRUD permissions) and ir.rule XML records (row-level domain filters). In ERPForAll (ADR 0035), both permissions and restrictions are unified into the ir.access format (matching Odoo 20’s consolidated design):

    • Rows with a group grant permissions (ORed across all groups held by the user).
    • Rows without a group impose restrictions (ANDed across all users).
    • Operation spelling follows Odoo 20’s 15 non-empty subsets of crud in strict c, r, u, d order (c create, r read, u update/write, d delete/unlink). Any unrecognized character (such as w) or out-of-order string fails parsing loudly with RowError::InvalidOperation.
    • Access domains compile directly into PostgreSQL SQL parameters ($uid, $company_ids, $now), evaluated once by the query planner rather than record-by-record in memory.

    4. Company consistency

    Section titled “4. Company consistency”

    Odoo’s company flags map one to one: _check_company_auto, check_company=True, _check_company_domain (here company_match) and with_company keep their meaning. What differs is the default and a few guarantees, all recorded in ADR 0044; the details are in company-consistency.md.

    AreaOdooERPForAll
    Check on by defaultA link is checked only when the model sets _check_company_auto and the field sets check_company=True; a forgotten flag is a silent cross-company link.Every stored many2one/many2many of a company-scoped model whose comodel is company-scoped is checked. Opt out with check_company_auto = false on the model or check_company = false on the field (Odoo’s behaviour exactly). A flag on a model without company_id/company_ids fails the registry build instead of being logged and skipped.
    Related readsA related field is read as superuser (related_sudo), so a user in company A reads a value through a record of company B.A related field that does not declare compute_sudo is read as superuser for permissions but only through records of the active companies (or of none), including the record its last relational field points to; a hop outside fails with Access. compute_sudo = true is the opt-out, compute_sudo = false the read as the caller. An explicit sudo() read keeps Odoo’s value.
    Validation under sudo()sudo() takes the ids of allowed_company_ids as given, so a company the user is not in is accepted.Company membership is validated under every elevation (One of the selected companies does not exist or is not one of yours.); the same check as for an unelevated environment.
    Duplicate idsallowed_company_ids=[1, 1] is accepted.A duplicated id is a Validation error naming it.
    Names in errorsDisplay names in the inconsistency error and in the debug listing of an access error are read as superuser.Names are read as the caller; an unreadable record is written <model>(<id>,). The debug listing shows a name only for records without company or in one of the principal’s active companies, and never names a company the user is not in. The hint texts and suggested_company are Odoo’s.
    System principalThe superuser takes any company list as given.Kept for the System principal the core creates. with_user(SUPERUSER_ID) from any other principal is refused (ADR 0164 A4, SPEC-PRIN-029): the environment stays the caller’s own user, with that user’s companies.

    Checklist: a link across companies on purpose gets check_company = false; a related field that must show a value across companies (a partner’s country on a document of another company) gets compute_sudo = true; a sudo().with_company(other) that relied on other being unchecked must be a company the user belongs to.

    Company contact fields

    Section titled “Company contact fields”

    res.company exposes street, street2, zip, city, email, phone, website and vat as writable related fields of partner_id (related = "partner_id.street", readonly = false, compute_sudo = true, so whoever may read the company reads these values, as in Odoo), so a read returns the company partner’s value and a write changes the partner. Known limit: a value the partner normalises on write (a bare website gets http://) reads back as written on the company until the next transaction. Odoo does the same, except that it stores email and phone on the company and computes the address from the partner. Creating a company with a name and no partner_id creates the partner and passes the contact values to it. country_id, state_id, logo and the report fields are not available yet; see docs/specs/base/company.md, section 4.7. An addon adds its own company contact field the same way: another related field plus an entry in the Settings > Companies form view. The company name does not follow the partner’s name yet (SPEC-PARTNER-060 is not implemented).

    5. Differences That Fail Loudly

    Section titled “5. Differences That Fail Loudly”

    Under the ERPForAll engineering standards, silent fallbacks, ignored errors, and permissive defaults are forbidden. The following table highlights common Odoo behaviors that fail loudly in ERPForAll:

    AreaOdoo BehaviorERPForAll Fail-Loudly ContractRelevant ADR
    Manifest ParsingBroken __manifest__.py files or missing keys are logged at DEBUG or silently cause the module to vanish from the list.Any syntax error, unknown key outside [extra], wrong value type, or invalid version stops startup with an error.ADR 0018 §1–2
    Missing DependenciesModules with missing dependencies are silently skipped or dropped from the installation graph.Discovery reports an explicit error listing all missing dependency chains and cycles.ADR 0018 §5
    Data File SchemaUnrecognized XML tags or attributes are ignored; misspelled attributes (modle=, <feild>) pass silently.Parser strictly enforces the element and attribute allowlist (RNG schema); unknown elements abort loading with file and line.ADR 0019 §3
    Boolean AttributesAny arbitrary string in a boolean attribute (e.g. noupdate="unknown") evaluates to True via str2bool.Only 1/0, true/false, yes/no, on/off are accepted; anything else fails loading immediately.ADR 0019 §2
    Comments in ValuesXML comments inside text values (e.g. <field>A<!-- c -->B</field>) silently drop content after the comment.Comments inside raw text field values are rejected loudly.ADR 0019 §3
    Expression EvaluationPython expressions in eval can fail at runtime or invoke unmonitored builtins.erp-expr parses expressions at build/install time; unexposed attributes or variables fail immediately (UnknownAttribute).ADR 0020 §1–3
    RPC ExposureAll public Python methods (not prefixed with _) are callable over RPC unless @api.private is added.Methods are private by default; calling an unexposed method over RPC returns 403. Only explicit #[rpc] methods are callable.ADR 0038 §1, ADR 0004
    RPC Effect ViolationsA @api.readonly method that writes to the database emits a warning and silently replays on a read/write cursor.Calling a method marked #[rpc(effect = read)] that attempts a database write fails loudly with a transaction error.ADR 0038 §2
    Translated View SelectorsExtension views can match elements by translated strings (<button string="Save">), breaking under other locales.Locating elements by translatable attributes (string="...") is strictly forbidden and rejected by erp-views.ADR 0027, erp-views
    Server Action PermissionsServer actions for object_write, object_create, etc., silently run with superuser privileges.All server actions run with caller rights unless an explicit, administrator-assigned run_as_superuser flag is present.ADR 0001, ADR 0009 §10
    PostgreSQL Version GateServer starts on older PostgreSQL releases (9.6+) and fails later with obscure syntax errors or degraded queries.Connection pool post-create hook enforces PostgreSQL 18+ (server_version_num >= 180000), refusing older servers with a typed error naming ADR 0028 and warning on PG19+.ADR 0028 §1
    Required Database ExtensionsMissing extensions (e.g. pg_trgm) silently cause trigram indexes to be skipped or fall back to sequential scans.Schema sync and DDL require declared extensions: declaring a trigram index (index = "trigram") when pg_trgm is not installed fails loudly with MissingExtensionError (Programming error).ADR 0028 §3
    Installation AtomicityOdoo commits after each module during multi-module install; a mid-way failure leaves a partially installed database.Install, upgrade, and uninstall execute in a single PostgreSQL transaction (all-or-nothing rollback on any failure).ADR 0009 §2
    Result Dictionariesvalues['x'] on a missing key raises KeyError; any code can add a key of any type to any row dict.Result rows are batches with one shared layout (erp_fields::rows): reading a key the rows do not have, a key absent in that row, or a row past the end is a Programming error naming the key, the row and the model; get_opt and contains are the explicit tests. Read a row like a dict with value.dict() (get, get_opt, contains, keys, iter, len), for Value::Map and Value::Row alike. Value is #[non_exhaustive]: an addon’s match on it ends with an arm that returns an error, never one that turns an unknown value into a normal one. The Rows override API (set, insert_key, remove_key, children_mut, from_maps) reaches web_read and read overrides in a later delivery.ADR 0052

    7. Backward Compatibility and Deprecation Policy (ADR 0096)

    Section titled “7. Backward Compatibility and Deprecation Policy (ADR 0096)”

    Unlike Odoo where upgrades between minor and major versions frequently break custom addon signatures, model field structures, and view inheritance without advance warning, ERPForAll enforces strict, machine-verified backward compatibility across minor releases (1.x):

    • Additive Public APIs: Core framework APIs (erp-sdk, erp-orm, erp-modules, erp-fields, erp-expr, etc.) must remain backward-compatible and additive within a minor series (1.x). Breaking method signatures or removing public API items within a minor series is strictly prohibited.
    • Compiler-Driven Deprecation Lifecycle: When an API is superseded, it must be annotated with #[deprecated(since = "1.X.0", note = "...")] directing developers to the preferred replacement. Deprecated APIs remain fully operational and tested for at least one complete minor release cycle before removal (or until 2.0).
    • Automated CI Compatibility Matrix (scripts/ci-compat.sh): A dedicated compat step runs in CI under scripts/ci.sh. It extracts the baseline two-addon extension suite from compat-baseline (which becomes v1.0.0 at the 1.0 release) and compiles and executes it against the current core codebase using an offline, local runner that reuses the workspace target directory. Deprecation warnings are emitted and reported in build logs, while any compiler error or runtime test regression fails CI loudly.
