    Declaring a model

    Section titled “Declaring a model”

    Book is a declaration type: it has no values and is never a record. Records are RecordSet<Book> values; the fields are associated constants (Book::NAME, Book::COPIES, Book::STATE) used to read and write typed values:

    books.vals() builds typed values for Book: only field handles of Book and of the models it inherits are accepted, and create/write validate every value against its field (selection keys, Char(size), digits) whichever API built it.

    Every data operation takes tx: &mut Transaction: one task owns a transaction, and its cache is shared by every environment (sudo, with_user, with_context). Run units of work through Orm::run, which commits and retries serialization failures and deadlocks (ADR 0008 §5); register side effects that must only happen after a successful commit with tx.after_commit(...).

    Eventful models

    Section titled “Eventful models”

    A regular model opts into transactional event metadata with eventful = true. The default is false; enabling it on any loaded declaration or extension enables the composed model. A later eventful = false does not disable another declaration’s opt-in. Rebuilding the registry after the opting-in addon is uninstalled removes that contribution; existing event rows are retained.

    Classical _inherit also contributes the parent declaration’s opt-in through the named child’s method resolution order: an eventful parent enables the named child, even if the child declares eventful = false. Delegation with _inherits does not compose this flag; the parent and child opt in independently, and a delegated-field mutation belongs to the parent model’s capture.

    Native code may also use ModelDecl::eventful(true); owned declarations use ModelDef::eventful(true). Data-only addons set eventful = true in their [[model]] table; non-boolean values are refused. Described WebAssembly declarations preserve the same boolean. The registry refuses opt-in on abstract models, transient models and the closed event namespace, with a diagnostic naming the model and enabling addon. General auto = false and SQL-view model declarations are not supported: their attributes are refused rather than treated as ordinary tables.

    The current candidate captures creates, scalar writes/upserts, stored computes scheduled by admitted mutations and supported eventful-root unlinks. X2many/relation and reserved-range bulk capture remain unfinished. A persisted event-relevant mutation requires an immutable operation identity from its entry point, including a non-eventful source whose changed dependency reaches an eventful stored compute. Events contain names and identifiers, not field values. Delegated fields belong to the parent model’s capture, and each model opts in independently.

    Delegation capture follows physical ownership even when one write supplies both inherited and local values. Each owner opts in independently. When a write also changes the delegation link, inherited values apply to the new parent; changing only the link does not invent a parent event. Equal physical business values emit nothing. Parent changes precede local child changes, and envelopes share the transaction’s final outbox INSERT. Shared-parent batches capture each actual parent target once.

    The bounded delegation acceptance also covers an ordinary authorized writer, explicit impersonation, a different flushing environment, effective company attribution, access denials and child-constraint rollback. These are specific tested paths, rather than every authority/company combination. See the current OUTBOX report for source-qualified evidence and remaining reentrancy limitations.

    Write capture compares actual database OLD/NEW values. An equal business write emits no event; automatic log-access and row-version bookkeeping does not itself create a business event. Stored computed/generated changes are included. The originating actor, operation and effective companies are retained when another environment later flushes or computes. Compute execution authority and the existing recompute-only write_uid rule remain separate from event attribution.

    A later event-relevant operation can settle earlier pending changes before staging its values, so repeated changes to one record retain operation order. Scalar batches remain set-based; all captured envelopes still share one final transaction INSERT. Nested event-relevant side-effect mutations inside an active mutation or compute currently refuse with a named S7 reentrancy error. This includes an inverse or async compute that tries to create/write another event-relevant record; ordinary computed output assignment is supported by the candidate. This refusal is an incomplete S7 case, not full outbox acceptance. No context flag disables required capture. See ADR 0126 for the contract.

    Scalar upsert on a declared business key captures returned physical outcomes: new rows emit create metadata, changed existing rows emit only actual business field names, and unchanged rows emit nothing. Overwrite, accumulation and floor actions retain their existing upsert semantics. Duplicate input keys map back to every input position but produce one capture per physical row; IDs are actual returned IDs, never inferred sequence ranges. Generated changes and deferred stored-compute writes retain the upsert writer’s attribution. Create/write overrides still do not run; an upsert override may wrap the base operation through super as before.

    Explicit input fields, conflict targets and context defaults obey the ordinary field write mask. Capture admission, callback/constraint/access failure after SQL, or cancellation prevents partial business/event commit. Envelopes split at the existing limits and share the final transaction INSERT. Relation commands, partitioned models and other pre-existing unsupported upsert shapes remain refused. See ADR 0134 and the source-qualified S9 report; this is producer support, not consumer delivery or full OUTBOX acceptance.

    An unlink tombstone contains only root IDs actually returned by PostgreSQL, with no field values or changed-field list. Missing rows and repeated deletions emit nothing. Batches split at 256 IDs per envelope and share the transaction’s final outbox INSERT. The actor, operation and companies come from the deleting environment, even when another environment commits.

    cascade_models names physical FK cascade/set-null targets, following cascade edges transitively. This summary comes from the current registry snapshot, including cold-cache targets; it does not list exact child IDs. Cycles and duplicate paths are deduplicated. More than 64 affected models refuses the unlink before destructive work; metadata is never truncated. Exact child IDs are planned.

    The candidate still refuses non-eventful roots that could indirectly change eventful rows, and eventful x2many or ancillary company-dependent/default/follow-delete effects outside the supported FK contract. These are explicit limitations. Deletion-triggered surviving stored computes retain the deleting origin; pending computes for records being deleted are dropped. Cancellation, caught capture refusal or a failed post-delete hook prevents the deletion from committing without capture. See ADR 0133 for this unlink boundary. Consumers, notifications and retention remain unfinished; this producer API does not establish event delivery.

    Exact signed bigint

    Section titled “Exact signed bigint”

    #[field(bigint)] stores a signed PostgreSQL int8 using erp_sdk::BigInt (ADR 0210). Construct native values with BigInt::from_i64(value) and retrieve the exact i64 with .get(). Zero is a stored value. Option<BigInt>::None stores SQL NULL; ordinary dynamic reads map NULL to bigint zero, while typed optional reads retain None.

    A static default can be a safe integer such as default = 0, or canonical decimal text such as default = "9223372036854775807". Dynamic values accept tagged BigInt, safe integers and canonical decimal strings. Floats refuse. Text has no plus sign, whitespace, redundant leading zeros or negative zero. Full-width domain operands use decimal strings and compare numerically, including IN/NOT IN and keyset/order operations. Company-dependent maps store bigint values as strings, with the same exact decoder.

    JSON-2 emits bigint values as decimal strings at every magnitude; see RPC. Grouping and aggregation are unavailable in this scalar delivery. Frozen WASM ABI1 also refuses the new scalar explicitly. A browser widget is not supplied by this scalar slice.

    Changing an ordinary stored field declaration from integer to bigint widens its column during module upgrade. Back up the database and use the normal module upgrade operation; schema changes and data loading share its transaction. Existing values and NULLs survive; declared indexes/constraints remain. Adopting a non-integer physical column also refuses and requires an explicit migration. Reverting the declaration to integer refuses: any narrowing requires an explicit migration that first checks every value. Do not use a relation field to store an unrelated 64-bit counter or job id.

    Native scalar prerequisite (in progress)

    Section titled “Native scalar prerequisite (in progress)”

    The outbox work adds purpose-neutral Uuid, Xid8 and TimestampTz scalar types and uuid, xid8, timestamptz field identities. This branch has focused prerequisite proof; it does not deliver an outbox, generated native fields, UI widgets or a complete native-field integration contract. Whole native-field integration and outbox acceptance remain incomplete.

    ScalarValue and input contract
    UuidAll 128-bit values, including nil; text requires lowercase canonical 8-4-4-4-12. No version, correlation or authorization policy is inferred.
    Xid8Exact unsigned 64-bit value; canonical decimal text, with no sign, leading zeroes (except zero itself), floating-point or signed intermediary.
    TimestampTzFinite whole-microsecond instant with explicit Z or numeric offset, normalized to UTC. The supported range is MIN_UNIX_MICROS through max_unix_micros() in its rustdoc, bounded by the pinned time library; full PostgreSQL extremes/infinity are unsupported.

    SQL NULL is distinct from nil UUID, zero xid8 and the Unix epoch. There is no implicit scalar default. Native literal field defaults refuse pending the future native static-default slice; explicit null/removal retains its meaning. A native schema type mismatch in either direction requires an explicit migration, including on an empty table. Schema sync never silently casts text to UUID/xid8 or attaches a timezone to existing naive Datetime values. Existing DateTime remains naive UTC; there is no implicit conversion to TimestampTz. Legacy RPC CorrelationId and IdempotencyKey parsers retain their existing case-insensitive UUID behavior.

    Frozen WASM ABI1 cannot discriminate these native kinds from ordinary strings. Explicit native fields, including NULL/empty requests, therefore refuse after the caller’s existing access checks, naming a future typed ABI major. Ordinary fields on the same model remain usable. The refusal follows the method chain, not the caller: once a WASM addon overrides create or write on a model, a create or write that sets one of that model’s native UUID, xid8 or timezone-aware timestamp fields is refused for every caller, native code and RPC included, because the value would have to cross the frozen ABI (a guest sees Unsupported; native code gets a Programming error naming the field and the future ABI major; an RPC client sees erp.programming). Install such an override only on models whose native fields are set elsewhere, or wait for the typed ABI major. Generic CRUD JSON, nested command ownership, compute metadata and tagged context values have separate admission boundaries; arbitrary user JSON strings are not guessed to be native values. The frozen WIT ABI remains unchanged.

    Native server_set, physical defaults, grant-contract publication and outbox storage remain disabled until a reviewed operational publisher identity boundary is enforced. No operational role migration or activation is authorized by this prerequisite.

Exclusion constraints (exclusions = [exclude(...)]), WITHOUT OVERLAPS keys (keys = [key(..., without_overlaps = "...")]) and extensions = [...]: see exclusions.md.

    Fill factor (ERPForAll only, ADR 0017 §1). fillfactor = N (10–100, percent) keeps 100 - N percent of each table page free so an UPDATE can put the new row version on the same page (a HOT update: no index entries written, less WAL). Without it the table keeps PostgreSQL’s default (100) or whatever a DBA set; with it, schema sync creates the table WITH (fillfactor = N) and applies changes with ALTER TABLE … SET, which affects pages written afterwards (existing pages keep their layout until the table is rewritten, e.g. VACUUM FULL). Measured on a 100,000-row table (docs/bench/m1-s7-orm-perf.md): scattered updates are all HOT from 90 down; rewriting every row in one statement (a mass recompute) needs about 50 to stay HOT and then runs 3–4× faster with a quarter of the WAL. Lower values cost disk and scan time, so use them for tables whose rows are updated often (order lines, stock quants), not for append-mostly tables (logs, posted journal items). Resolution follows the model’s declaration order (MRO) like order: the newest declaration that sets fillfactor wins, so an #[extend] in an addon loaded later can tune a model it does not own, and an addon loaded earlier cannot override it.

    Shared id sequence (ERPForAll only, ADR 0058). id_sequence = "ir_actions_id_seq" makes the table’s id draw from that named sequence instead of its own identity; every model naming the same sequence shares it, so their ids never collide (the action models use it to share one id space, as Odoo’s table inheritance does). Schema sync creates the sequence (bigint, increment 1, no cycle, owned by no column; an existing sequence of another shape is refused) and sets it as the id default of new tables. The name is checked at compile time (a PostgreSQL identifier of at most 63 bytes, given once). It is set per model, never inherited through inherit, and refused on abstract and partitioned models, on a name that is a table, a many2many relation table or a table’s own identity sequence (<table>_id_seq), and on an existing table whose id is an identity or draws another sequence (converting a populated table is a data migration). It costs one shared sequence per insert batch, so keep it to low-volume tables.

    Signal triggers (ERPForAll only, ADR 0035 decision 4). The access policy every process serves is compiled from database rows (ir.access, groups, capability mappings, field groups); when one of those rows changes, every process must rebuild it. signal_triggers = [("_name", "policy")] makes schema sync put a statement-level trigger on the model’s table that records one policy change per transaction, whoever writes: the ORM, raw SQL, a foreign-key action. Add relation = "<many2many field>" to put it on that field’s relation table instead, and update = false to leave updates out (inserts and removals still count). The function the trigger runs belongs to the core: you name the table and the signal, never SQL. base declares them on its policy tables; an addon needs one only for a table whose rows are compiled into the policy. A table an access rule reads through a sub-select (a share table read by a grant) needs none: the predicate reads it fresh in every statement.

    A relation trigger must name a stored many2many of the model itself (not one inherited through _inherits); anything else fails the registry build with a Programming error naming the field. A process that changes such rows decides correctly inside its own transaction only if the model is also registered in erp_sdk::access::POLICY_SOURCE_WRITES (see security.md).

    Follow-delete triggers (ERPForAll only, design m2-s3.md §6.1). A table whose rows are mirrored in a key table (the action types and ir_actions) or summarized in a named cache must follow every deletion, also the ones the database makes by itself through ondelete = "cascade", which run no unlink override. follow_deletes = [("_keys_follow", cache = "actions", key_table = "ir_actions")] puts a statement-level AFTER DELETE trigger on the model’s table that deletes the key table’s rows with the deleted ids and bumps the named cache’s generation once per transaction (every process drops its cached values at its next transaction); relation = "<many2many field>" puts one that only bumps the generation on that field’s relation table (its rows go when either side is deleted). The ORM’s unlink follows the cascades of the registry into such tables and invalidates the cache in the deleting transaction too. cache and key_table may name &str constants; the cache name is [a-z0-9_], at most 40 bytes, and the key table the table of another model of the registry, checked when the registry is built; the key table needs a stored char field type naming each key row’s model (only the trigger’s own model’s key rows are deleted). TRUNCATE of a followed table is refused (it cannot be followed), and a DELETE your transaction sends as SQL on one invalidates the cache in that transaction too.

    Default values and default_get

    Section titled “Default values and default_get”

    A field’s default is a literal (default = <literal>) or a function (default_fn = path). The ORM asks for defaults through the model’s default_get method: create for every field the values leave out, the web client’s forms and onchange for a new record (CRUD §4.5, SPEC-CRUD-005 to SPEC-CRUD-008).

    A default function has the signature fn(&DefaultContext) -> Value: it receives the current user id (ctx.uid) and returns a dynamic value, which is normalized like any other default (below).

    Resolution order (CRUD §4.5)

    Section titled “Resolution order (CRUD §4.5)”

    For each requested name, the first matching rule wins:

    1. Context key default_<name> (SPEC-CRUD-006), set with with_context([("default_state", Value::from("done"))]). Returned even when the name is not a field of the model.
    2. Other names that are not fields of the model are skipped (never an error).
    3. User defaults from ir.default: not shipped yet (M2, data layer). Until then the field’s own default applies; nothing is substituted.
    4. The field’s declared default (SPEC-CRUD-005): default = <literal>, or default_fn = path (fn(&DefaultContext) -> Value). default = none in an extension drops an inherited default.
    5. Company-dependent fallbacks from ir.default: not shipped yet (M2), as step 3.
    6. Fields delegated to an _inherits parent (SPEC-CRUD-007): the parent model’s own default_get (its overrides included), unless the field is Odoo’s NO_ACCESS (groups = ".") outside superuser mode.

    Normalization and overrides

    Section titled “Normalization and overrides”
    • Normalization: scalar values are converted to the field’s type (a value of the wrong shape is a Validation error naming the field). x2many defaults become command triples: one SET of the linked records followed by one CREATE per new line (False gives [[6, 0, []]]).
    • Overriding default_get: an addon can override default_get like any model method; create and the web client go through the override too:
      Only add names that were asked for: create writes every field of the result that its values leave out, and a returned name that is not a field is a Programming error.

    Database default of a fail-closed flag

    Section titled “Database default of a fail-closed flag”

    ORM columns have no database default: the ORM applies defaults before the INSERT (ADR 0017 §5). A row written with plain SQL (bootstrap statements, migrations, an operator’s script, a test fixture) therefore gets NULL in a column it leaves out, and a required column refuses it. For a boolean that must fail closed whoever writes the row, such as the share flag the company restriction of res.users escapes through, declare db_default (ERPForAll only, ADR 0171):

    • Schema sync keeps the static default as the column’s DEFAULT: on a new table, on a new column (the fast default is not dropped) and on an existing column that lacks it or has another value (ALTER COLUMN … SET DEFAULT, catalog-only). An extension that declares db_default = false makes the next sync drop it again.
    • Only a stored, required boolean with default = true or default = false, not company-dependent and not generated; anything else is a Programming error at registry build that names the field and the missing condition. Models declared in models/*.toml and WebAssembly addons cannot set it.
    • The ORM still writes the column in every create (the static default when the caller leaves it out), so ORM and SQL writers store the same value. Use it for fail-closed flags only, not to move ordinary defaults into the database.

    Searching

    Section titled “Searching”

    Domains are Odoo’s: build them in Rust or parse list syntax sent by a client.

    • Archived records (active/x_active false) are left out unless the domain mentions the active field, the context sets active_test to false, or SearchOptions::active_test(false) is given.
    • The access policy’s record rules are added to the domain and evaluated in SQL; nothing is filtered in memory.
    • Relative dates ('today', 'now -1d', '=1d' …) are resolved in the user’s timezone (context tz). =week_start uses Sunday until languages arrive.
    • Every operator on stored fields, paths (partner_id.country_id.code), any/not any, child_of/parent_of, display_name through rec_names_search, and order on columns, selections (declaration order) and many2one fields (by the comodel’s order). Field search= methods are refused with a “not supported until” error.
    • records.fetch(&mut tx, Some(&["name"])) loads what is missing for a recordset in one query per batch; read leaves out records that were deleted. Outside superuser mode both evaluate the record rules in SQL even when every value is already cached.
    • Order of ties. Unless the order already contains id, id is added as the last sort key, so records with equal keys come back in the same order on every page. Odoo leaves ties to PostgreSQL (undefined and possibly different between pages); this only fixes what Odoo leaves open.
    • Negations are not index-friendly. !=, not in, not like and not ilike on a nullable column compile to (… OR col IS NULL) so that records without a value match, as in Odoo; such conditions usually scan. Prefer a positive condition when a selective index matters.
    • like patterns. like/ilike wrap the value in %…%; % and _ inside the value are wildcards and \ escapes them (name like '50\%' finds a literal 50%). =like/=ilike use the pattern exactly as given. Escape user input before using it as a literal.
    • Accents. With OrmConfig::unaccent on, ilike ignores accents. Schema sync then creates an immutable erp_unaccent() over the unaccent extension (it must be installed) and trigram indexes use the same expression, so they serve those searches.
    • Plans. A search whose domain has values runs as an unnamed statement that PostgreSQL plans for those values (as it plans Odoo’s literal SQL); reads by id and searches without values are prepared once per connection and reused (ADR 0017 §3). Nothing to do in addon code.
    • “queries overflow the depth limit”. An addon crate that awaits a search deep inside its own async code (several layers of async fn around search, search_with or search_read) can stop compiling with rustc’s error: queries overflow the depth limit! while rustc lays out the nested future. Until a boxed boundary is put at the search entry (planned), raise the limit at the top of the addon crate’s lib.rs (#![recursion_limit = "256"], as the base addon’s res_users doctest does), or box the awaited call in your own code (Box::pin(books.search(&mut tx, &dune)).await?). Neither changes what runs.

    Deep pages: keyset pagination

    Section titled “Deep pages: keyset pagination”

    OFFSET 40000 makes PostgreSQL read and throw away 40,000 rows; search_after continues from the last record of the previous page instead, so page 1,000 costs what page 1 costs (measured on 1,000,000 rows: 0.12 ms instead of 307 ms, docs/bench/m1-s7-orm-perf.md §4), and records created or deleted before the cursor do not shift the pages.

    • next is None on the last page (a page shorter than the limit). The cursor holds the order and the last record’s key (one value per order term, id last); a cursor of another order, or whose values do not fit, is a Validation error. offset must be 0 and limit positive.
    • Order terms: the model’s stored columns (text, numbers, dates, booleans, selections) and many2one fields by id (partner_id.id, or a comodel whose order is id). Ordering through a comodel’s order (partner_id when partners are ordered by name) is refused: order by a field of the model instead.
    • Index use: give the leading order term an index. When every term has the same direction the next page is one range scan ((a, id) > ($1, $2)); a nullable leading term whose NULLs come last adds a second, IS NULL query on the one page that reaches them. Orders mixing directions are bounded by their leading term and filtered within it.

    Reading large results in windows

    Section titled “Reading large results in windows”

    search_with and read_rows keep every record they read in the transaction’s cache until it ends: right for a page or a form, wrong for an export, a report over a year of lines or a batch job over a whole table. stream reads the records of a domain window by window instead. Each window is a Rows batch equal to read_rows of its records; before the next window is read, the window’s records leave the cache and its buffers are reused, so a stream holds one window whatever the result size (measured: the same peak for 20,000 and 40,000 lines, docs/design/perf-stream-window.md §5).

    • What a domain stream sends. The first window rides one flight: DECLARE erp_cN NO SCROLL CURSOR WITHOUT HOLD FOR <the search> and FETCH, with SET LOCAL cursor_tuple_fraction = 1 in front for the transaction’s first stream (the setting lasts until the transaction ends, so it is sent once per transaction, and again only after a rollback to a savepoint opened before it undid it; it steers the planner of every later cursor of the transaction too, DECLAREs only, plain queries are not affected). Every further window is one FETCH, one round trip. The search is search_with’s: record rules, the active test and the order (the model’s unless StreamOptions::order is given). Pending writes are flushed before the cursor is declared. stream_records reads its recordset as it is and refuses order and active_test(false).
    • Snapshot. The cursor reads the transaction’s snapshot: rows other transactions commit while you read are not seen, rows this transaction wrote before stream are.
    • Writes inside the loop. A cursor keeps the rows of its DECLARE, also for what the transaction itself writes later. So once the transaction changed the streamed model after the DECLARE (an ORM write or unlink once flushed, a stored compute written back, a raw UPDATE, DELETE, INSERT or MERGE of its table or of a many2many link table it is a side of, a DELETE of a table whose rows its many2one points at with ondelete cascade or set null, followed through further cascades, a data statement on a table the registry does not know, any other raw statement the ORM cannot attribute, an invalidation, a rollback to a savepoint), each later window takes only the ids from the cursor and reads its values fresh by id, exactly as stream_records does: one more statement per window, values current. What happens to the rows the writes touch, on both sources: a record changed so that it no longer matches the domain still arrives, with its new values (the record list is the one of the DECLARE; stream_records has no domain); a record deleted is left out (like read_rows of a deleted record); a record created is not in a domain stream (it was not in the DECLARE’s result) and is in stream_records only if it is in the recordset. For a restricted user, once the policy or a row its record rule reads changed (the streamed model or a model the rule reads), each window’s ids are checked against the rule again (one statement) before it is lent: a record the rule no longer lets the user read is refused with the Access error read_rows gives, the same on both sources. A window whose every record was deleted is skipped: the next one is read.
    • What the ORM does not see. The ORM knows what a statement may change from the statement itself. Two kinds of writes do not show in it: a function called from a SELECT that writes (SELECT my_function(...)), and a database trigger that writes other tables. After such a statement the cursor would lend the rows of its DECLARE for the tables written behind the ORM’s back. Code that runs one inside a stream loop, and an addon that installs such a trigger, must call Records::modified_external for affected stored scalar columns after settling prior ORM work, so source caches and dependents update. When no dependency notification is needed, Transaction::invalidate_model (or invalidate_records) remains available. These operations move the model’s tick and the next window reads fresh values.
    • Raw SQL the ORM cannot read with certainty. The ORM reads raw SQL with PostgreSQL’s own lexical rules. What it is not certain about it treats as a statement that may change anything (every stream reads fresh afterwards, an onchange scope opens its savepoint), and a read-intent transaction refuses it with an error saying so: a U&'…' string or U&"…" name, a backslash outside an E'…' string (write E'a\\b', as the ORM’s own literals do), a stray $, and unterminated text. The ORM reads statements as a connection with standard_conforming_strings = on and client_encoding = UTF8 does: the pool refuses a connection that opens with other values, with an error naming the setting (for standard_conforming_strings a role or database default; client_encoding always opens as UTF8, since the driver asks for it at connect, which outranks role and database defaults, and the server applies it after the connection’s options). When the server reports a new value of either setting on the connection (whatever caused it: SET, set_config, RESET, a function, dynamic SQL in a DO block; also before the transaction got the connection, by code that used a pooled connection directly), every later raw statement of the transaction object is treated as one that may change anything, a read-intent transaction refuses raw SQL from then on, and the connection is closed instead of going back to the pool. Code that takes a connection from the pool directly (outside a transaction object) may get such a connection before a transaction closes it: write text in its SQL as E'…' (as erp_sql::literal does) or bind it as a parameter, never as a plain '…' string with a backslash.
    • Functions a read-intent transaction refuses by name. pg_notify, set_config, the advisory lock and unlock functions, pg_terminate_backend, pg_cancel_backend and the dblink functions: READ ONLY allows them, but their effect outlives the call or reaches past the transaction. A function of your own that calls one of them inside is not seen; declare effect = write for an entry point that calls it.
    • Savepoints. A rollback to a savepoint ends the cursors declared under it (using the stream then is a Programming error). A FETCH made inside a savepoint that is rolled back is not undone by the server: a cursor does not rewind, so the next next refuses (fetch outside the savepoint, or start a new stream). A FETCH inside a savepoint that is released is kept.
    • Window size. By default 2,000 rows first (1,000 when a field is text, html or json), then about 1 MiB of rows per window, between 1,000 rows and OrmConfig::prefetch_chunk. StreamOptions::fixed_window(n) takes 1,000 ≤ n ≤ 10,000 (never 0 = unlimited, never below Odoo’s export batch of 1,000) and is refused when above prefetch_chunk. The bound is in rows, not bytes: the 1 MiB aim follows the bytes of the window before, so a window that follows narrow rows can hold up to prefetch_chunk (at most 10,000) wide ones; the worst case is that row count times the widest row.
    • The window is lent. It is valid until the next next call. Keep values you need by copying them out; a clone of the batch stays valid too (the stream then makes new buffers for the next window, counted by buffers_renewed). Writing to records inside the loop is fine: the writes are flushed before the next window (see “Writes inside the loop”). Creating a new (in-memory) record inside the loop is refused, because the window is dropped from the cache and a new record cannot be. A call to next dropped before it finished (a cancelled task, a timeout) while its FETCH was in flight leaves the cursor’s position unknown: the stream stops and the next call says so.
    • Several streams. Streams of one transaction may be read in turns (two exports, a stream inside another’s loop); each equals read_rows of its records. A transaction holds at most 32 open cursors (Transaction::set_cursor_limit changes it for that transaction object); one more stream is refused with a Programming error naming the setting. The cursor names erp_c1, erp_c2, … are reserved: raw SQL must not declare cursors with the erp_c prefix.
    • Closing. A stream that is finished, closed (close) or dropped asks the transaction to close its cursor; the CLOSE goes out with the transaction’s next statement (no round trip of its own), and nothing is sent when the transaction ends first. A stream belongs to its transaction: using it with another one, after a commit, rollback or lost connection, or after a rollback to a savepoint it was declared under is a Programming error. Streams are refused inside an onchange.
    • The transaction stays open between windows. Between two FETCHes the transaction is idle but open, and holds its snapshot: PostgreSQL’s idle_in_transaction_session_timeout (if the server sets one) ends a stream whose consumer is slower than it; the snapshot holds back VACUUM (dead rows of every table stay until the transaction ends: bloat on a busy database); on a hot standby, a long stream can be cancelled by a replication conflict (max_standby_streaming_delay). Keep the work per window short and the transaction no longer than the stream; long exports belong in the export service (planned).
    • query_each runs raw SQL like Transaction::query (prepared, counted, no access rules, the read-only guard applies) and lends each row as an SqlRow (len, column_name, column_type_name, try_get into an SqlValue type: integers, floats, bool, text, bytes, JSON, Decimal, Date, DateTime, each also as an Option). The memory of a large answer is one received batch, whatever the row count. An error returned by the closure stops the rows; the transaction goes on.

    Working with recordsets in memory

    Section titled “Working with recordsets in memory”

    Recordsets are immutable collections of record ids sharing an environment and a prefetch set. Typed (RecordSet<M>) and dynamic (Records) recordsets offer the same operations as Odoo’s recordsets; a RecordSet<M> also gives access to every Records method.

    • Set operations:
      • concat(&other) (+): both recordsets in order, duplicates kept (SPEC-RSET-016).
      • union(&other) (|): union in first-occurrence order, de-duplicated (SPEC-RSET-017).
      • intersection(&other) (&): ids of self that are in other, de-duplicated, in self’s order (SPEC-RSET-018).
      • difference(&other) (-): ids of self that are not in other, self’s duplicates kept (SPEC-RSET-018).
      • concat_all(sets) / union_all(sets): the same over an iterable of recordsets (SPEC-RSET-020).
      • is_subset(&other) (<=) / is_strict_subset(&other) (<) (SPEC-RSET-013).
      • Operands of different models are an error (SPEC-RSET-019).
    • Environments (each returns the same ids on a new environment; the transaction’s cache is shared):
      • records.sudo(flag): superuser mode on or off, same user id. Turning it on removes the default_* keys from the context (SPEC-ENV-004).
      • records.with_user(uid): another user; superuser mode only when uid is the superuser (SPEC-ENV-005). Who may switch is decided on the principal of the environment you call it on (ADR 0164 A4, SPEC-PRIN-029): the System principal switches to anyone, any principal to its own user, and another user only when it holds the capability principal.impersonate (base maps it to Settings administrators); otherwise the first use of the new environment (a read, a write, a model check, a scoped block, a job enqueue, a capability question) fails with Access “user A may not act as user B: with_user needs the capability ‘principal.impersonate’”. A switch to the superuser id from any principal but System is always refused (“only the system principal may act as the superuser …”), also from sudo(true); the refused environment stays the caller’s own user and never reports su(). To ask whether another user is in a group, call tx.user_has_group(&env, user, "module.group") instead of switching; to open a transaction or an environment for a caller, use orm.begin_caller(user) / orm.env_caller(user, context) (or BeginOptions::caller, PrincipalHint::caller), which refuse the superuser id.
      • records.with_context(pairs): the context updated with (key, Value) pairs (tz, lang, active_test, default_* …) (SPEC-ENV-006).
      • records.with_env(env): the same ids on a given environment.
      • records.with_prefetch(ids): another prefetch set (None: the recordset’s own ids) (SPEC-ENV-028).
    • Results keep the input’s order and duplicates and share its prefetch set, so a field read through one result (or one group) is loaded for all of them. Each operation reads a field once for the whole recordset: at most one query per field group when the values are not cached, none when they are. Write loops over recordsets with these operations instead of reading records one by one.
    • filtered_domain evaluates the domain on the values in memory with the same rules as search (NULLs, 0/'' treated as “not set”, negations): search(D) and search([]).filtered_domain(D) agree. It also works on non-stored computed fields and display_name, and follows relational conditions (any, paths, x2many in, child_of): the targets are filtered in memory on the comodel, once for all records; any! and bypass_search_access fields look at the targets as superuser. Text follows the C collation of ERPForAll databases: code-point order, and ilike folds ASCII letters only (É does not match é unless OrmConfig::unaccent is on).
    • sorted takes the same order syntax as search and places NULLs the same way (last ascending, first descending, unless nulls first/nulls last). It is stable, also with reverse. Like Odoo’s in-memory sort it differs from search in three ways: selections sort by key text, not declaration order; NULL integers/floats/amounts count as 0; a many2one is ordered by its comodel’s order read with your rights. Text compares by code point (the C collation of Odoo databases).
    • Closures that need no database access have _by variants: filtered_by, sorted_by_key, grouped_by. To filter or sort on field values, use the field forms above.
    • exists() always asks the database (one query per batch of ids); it ignores record rules and active and never touches the cache. New records always exist.
    • Locks use SKIP LOCKED: they never wait. lock_for_update fails with a Lock error when any row is held by another transaction or deleted (rows locked before the error stay locked until the transaction ends); try_lock_for_update returns what it could lock, in recordset order, at most limit records (new records count as locked and come first). allow_referencing = true takes the weaker FOR NO KEY UPDATE lock, which still lets others insert rows pointing at these records.

    Models whose columns only their owner adds

    Section titled “Models whose columns only their owner adds”

    A model can protect its table: with owner_only_stored_fields on the declaration that creates it, only that addon (the owner) and the co-owner addons it names may add a column to the model or change the storage, type, relation or generated expression of one (ADR 0166 decision 7). Integrity code that compares or guards the table’s columns can then rely on them. The policy is native only: model files, WebAssembly descriptions and overlays cannot set it, and an extension cannot set, replace or widen it. A co-owner must be a known addon (installed, or linked into the build) and, when installed, depend on the owner; one that is linked but not installed has no effect. #[extend] refuses the attribute.

    Any other addon still extends the model with fields that have no column of their own: nonstored computed or related fields, VIRTUAL generated fields (ADR 0062), one2many fields, and many2many fields on a relation table of its own; it keeps its data in a companion model of its own. A stored column from it (ordinary, stored computed or related, STORED generated, translated, row_version) is refused with Programming, naming the addon, the model and field, the owner and the declaration (with its source file and line when it has them), in this form:

    The same holds when the column arrives through a mixin that addon adds or extends, through its model files, or as a custom x_ field (dropped and reported under DropBroken). store = true alone is not the test: a VIRTUAL generated field has it and stores nothing.     Extending a table that already holds many rows

    Section titled “Extending a table that already holds many rows”

    Adding an indexed field, a many2one, a stored computed field or making a field required changes the table of a model that may already hold millions of rows. Schema sync keeps the install transaction short on such tables (ADR 0009 §2): when the table has more rows than the host’s threshold (100,000 by default), the work that would scan it runs after the install commits, as post-commit steps:

    Your changeIn the install transactionAfter the commit
    #[field(..., index)], a many2one (indexed by default), indexes/unique_indexesnothingCREATE INDEX CONCURRENTLY
    a many2one (foreign key)the key, added NOT VALID (new writes are checked)VALIDATE CONSTRAINT
    a field becomes required without a defaultthe not-null constraint, added NOT VALIDVALIDATE CONSTRAINT
    a field becomes required with a defaultnothingNULLs filled with the default in batches, then the constraint added and validated

Until a step has run, its index is missing (a unique_indexes entry does not reject duplicates yet) and records not reached by a backfill read an empty value for the new field. A step does not keep your users waiting: when it would wait for a lock while holding readers or writers up, it gives up after a short wait (10 seconds by default), and the next schema sync plans the unfinished work again.

    Methods and overrides

    Section titled “Methods and overrides”

    The addon that owns the model defines a method:

    Another addon overrides it, and callers use the generated BookMethods trait:

    • #[method] introduces a method; #[method(override)] overrides it and receives sup: Super as its last parameter (super() in Odoo). Arguments after tx must be owned types.

    • The newest addon in load order runs first; sup.call reaches the previous one.

    • #[methods(Book)] impl Book generates a trait BookMethods for typed calls (books.label(&mut tx).await?), available on recordsets of Book and of models inheriting it.

    • A method defined by an addon you do not depend on can still be called by name: this.call::<(), i64>(tx, "bar", ()).await?.

    • create and write are overridable the same way: create takes Vec<RawVals> (one entry per record to create) and returns Records; write takes RawVals. Overrides receive whole recordsets and value lists: never assume a single record.

    • copy, copy_data, name_create, action_archive and action_unarchive are overridable model methods through the same dispatch chain:

      • copy takes default: Option<ValueMap> and returns Records (the newly created duplicate records);
      • copy_data takes default: Option<ValueMap> and returns Vec<Option<ValueMap>> (field mappings ready for create);
      • name_create takes name: String and returns (i64, Arc<str>) (the id and display name of the created record; requires _rec_name);
      • action_archive and action_unarchive take no arguments and return () (writing active = False or active = True on active or inactive records; requires an active field).

      Copy traversal has fixed limits of 16 nested one2many levels and 10,000 distinct records; exceeding them returns a validation error. Group-restricted copyable fields require read access and otherwise refuse the copy. Stored translations are not yet copied as translation maps.     • Of the recordset operations, only exists (no arguments, returns Records) and filtered_domain (takes a Domain, returns Records) can be overridden, as Odoo addons do (for example to answer exists from a cached id set, or to rewrite a condition before calling sup). filtered, mapped, sorted, grouped, the set operators and ensure_one are final.

    These are reported at startup with the file and line of the implementations involved:

    • two implementations of one method with different signatures;
    • an override with no definition below it;
    • two plain #[method] definitions in one chain (the later one must be #[method(override)]);
    • a #[methods(Model)] block in an addon that has no #[model]/#[extend] of that model;
    • one addon implementing a method twice.

    Notify the ORM after external SQL

    Section titled “Notify the ORM after external SQL”

    Trusted native code that changes a model’s stored scalar columns with SQL must notify the ORM about the affected records and fields. This includes columns maintained by a database trigger. Settle pending ORM work before the SQL, then call modified_external:

    The notification drops the named source values from cache and runs the same dependency walk as an ORM write. Stored computed dependents become pending; non-stored dependents lose their cached values in every context, including dependents reached through unchanged relations. Normal reads and commit settle the computed values. The call itself neither flushes nor writes; relation traversal may issue SELECTs. It also advances the affected model’s stream generation, so an already-open cursor cannot put an earlier value back in cache.

    This method performs no access authorization and grants no read or write right. The SQL writer must authorize its operation, identify all affected rows and columns, and record any required source audit or business events. Notification creates no source audit or event record. Normal later dependent recomputation retains its existing provenance requirements. An error after partial notification leaves the transaction rollback-only; rollback before continuing.

    Only physical stored scalar columns owned by the recordset’s model are admitted. Unknown fields, delegated projections, non-stored fields and x2many fields fail by name. Relationship source columns are not supported yet: changing a parent link requires information about its previous owner. Notification still follows dependencies through links that did not change. Draft records and notified fields with dirty values or pending computations are refused; settle them before running external SQL. Resolve any principal switch before that SQL too: notification validates provenance without a flushing resolution step. Read-only generated-input callbacks also refuse notification. Catching that refusal does not let the callback finish successfully.

    The method is final and native-only; it has no RPC, script or WASM route. Duplicate names/ids are coalesced, and empty admitted input does nothing. Field names are validated even when the recordset is empty. invalidate_records remains a flushing cache-invalidation operation; it does not replace dependency notification after an external change.

    Computed fields

    Section titled “Computed fields”

    A computed field names its compute method; the method lives in a #[methods] block and declares what it depends on:

    • Sync computes (plain fn) run once per batch of records over values the ORM loaded first. They may read only their depends, the fields listed in reads = [...] (read without triggering a recompute) and the fields computed by the same method; anything else is an error. batch.set_all(field, value) assigns every record.
    • Async computes (async fn) are for computes that search, aggregate or create records. They receive the whole batch as a recordset and assign through out:
      They also run once per batch, never per record.
    • Several fields may share one compute method (they must all be stored or all non-stored).
    • depends lists fields of the record, or paths through relational fields ("line_ids.price_subtotal", "partner_id.country_id.code"). A sync compute reads the values its paths reach with batch.value_of(Field, id) (or values_of for several ids); the ORM loads them for the whole batch first, one query per step at most:
      Every prefix of a path is a dependency: changing a line’s price, moving a line to another order (both orders) or creating a line marks the order. A record’s x2many reads like the record would see it (archived lines left out). Reading a field that no path reaches is an error, as for the record’s own fields; reads = [...] takes paths too.
    • A field that depends on itself through a relation ("parent_id.display_name") is recursive: it is computed level by level, parents first, and a whole hierarchy settles in one flush.
    • Changes on regular models never mark fields of transient models (a wizard’s path stops where it enters a regular model).
    • Marking dependents through relations reads the relation from the cache when it can (the inverse field of a one2many, a mirror many2many), otherwise one query per relation step, for all the changed records at once; nothing is read when every dependent behind a step is non-stored and not cached.
    • Override a compute in another addon with #[compute(override, depends = [...])] and a last parameter sup: ComputeSuper, sync or async (an async compute receives the async variant, AsyncComputeSuper); call sup.call(batch)? (sync) or sup.call(tx, this.as_records(), out).await? (async) for the inherited value. The dependencies of every implementation add up. A depends = [...] on the field itself replaces them:
    • Field options: store, readonly = false (a written value is kept until a dependency changes), inverse = "_method" (an async #[method] with no arguments that writes the dependencies back), compute_sudo, depends_context = ["key", "uid", ...] (non-stored values cached per context), related = "partner_id.country_id.code" (a path, or a field of the same record; computed as superuser by default, writable with readonly = false: writing it writes the target record, when both records are database records or both are new). Non-stored related fields are searchable (partner_name = 'x' searches partner_id.name; a condition matching empty values also matches records without a partner).
    • Sensitive display-name inputs can use Env::label_reader() to obtain the original consumer of an internally elevated label read, or the current environment for an ordinary read. Check permissions and read those inputs through this environment. Declare depends_context = ["label_reader", ...] to separate cached values by its principal binding, policy snapshot, resolution/groups and validated companies. This reserved key is derived by the engine; a context dictionary cannot impersonate a different reader. It does not replace ordinary data dependencies or authorization checks (ADR 0195).
    • Stored computes are computed before the INSERT of create (one statement per batch of records), unless the field was given and is editable. Through relations, only paths of many2one fields qualify (partner_id.name: the partners are read for the whole batch); a dependency through an x2many (line_ids.price) is computed after the lines exist, at the next flush or read. Async stored computes are computed at the next flush or read. The full rules, and what precompute = false and precompute = true mean, are in Stored computes at create.
    • Writing a value equal to the cached one triggers nothing. Recomputation happens lazily: when the field is read, or at flush (before commit, before savepoints, or tx.flush_fields(...)).
    • A flush that keeps finding new work (computes creating records that need computing, and so on) fails after OrmConfig::max_flush_rounds rounds instead of committing a half-computed state.
    • When a compute does not assign a stored field, the record keeps its current value (as in Odoo), an in-memory record the value it holds (a form’s value); only a record with no value at all gets an empty one. A non-stored, readonly field must be assigned for every record: otherwise reading it is an error.
    • Computations triggered by a flush run in the transaction’s environment (tx.env()), not in the environment that changed the dependencies; rows written only by such a recompute get that environment’s user as write_uid. Computes triggered by a read run in the reader’s environment. compute_sudo fields always compute as superuser, keeping the uid.
    • Dependencies may include display_name; it follows the model’s rec-name field.
    • precompute = false on a stored computed field keeps it out of the INSERT; a compute that reads (or depends on) a field computed after the INSERT is computed after it too.

    Stored computes at create

    Section titled “Stored computes at create”

    A stored computed or related field is written by the INSERT of create, not by an UPDATE after it, whenever its inputs are known when the row is inserted. No declaration is needed: this is the default (ADR 0053). Odoo does it only for fields declared precompute=True and writes every other stored compute of a new row a second time at the flush.

    Known at the INSERT are the row’s own fields (given or defaulted), the stored computes of the row that are themselves computed before the INSERT, and fields reached through many2one fields only (partner_id.country_id.code: the partners and countries exist; they are read once for the whole batch, nothing when they are cached).

    Computed after the INSERT (at the next flush or read, one UPDATE per batch) are:

    • async computes (they may query);
    • computes that read display_name;
    • computes with a dependency through a one2many or a many2many (line_ids.price_subtotal: the lines of a new record are created after it);
    • fields declared precompute = false;
    • every field that reads one of those. The fields of one compute method decide together: if one of them is computed after the INSERT, all of them are.

    At create, a readonly precomputed field ignores a given or default value and is always computed; an editable one keeps a given or default value, and giving one editable field of a compute method leaves the method’s other fields empty (as in Odoo).

    Inverses and related writes in the same create. A field computed before the INSERT without a declaration is recomputed at the flush when an inverse method or an editable related field given in the same create changes one of its inputs, so the stored value is the one Odoo computes at the flush; only that case costs an UPDATE. A field declared precompute = true keeps the value it was given before the INSERT for the rest of the create, as in Odoo.

    precompute = false opts out: the field is computed after the INSERT, together with everything that reads it. It is rarely needed; use it when the value must be computed on the stored row, for example by an async compute that queries it.

    precompute = true is an assertion, not a switch. It does two things: the value computed before the INSERT is kept for the rest of the create (inverses and related writes do not recompute it, as in Odoo), and the ORM refuses to build (ErrorKind::Programming) when the graph cannot honour it, naming the field and the first input that blocks it. Declare it where you rely on the value being in the INSERT, for example a field that a record rule on create reads: a later change that moves the field after the INSERT (a new dependency through a one2many, say) then fails the build instead of passing unnoticed. It is not needed for a field to be precomputed:

    Declaring precompute on a field that reads label, or on a total over line_ids, fails at build with a one-line error that names the field, says it cannot be computed before the INSERT, names the dependency it reads (here line_ids.price through the one2many library.book.line_ids, whose lines are created after the INSERT) and says that precompute over one2many lines is not supported yet.

    Odoo only warns there and turns precompute off, so the field is silently written twice; when moving such a field from Odoo, drop the declaration (or the dependency that blocks it).

    Errors that poison a transaction

    Section titled “Errors that poison a transaction”
    • A Validation error raised by create, write, a recompute or a flush (a constraint, a value the converter rejects, a database constraint) leaves the transaction unable to commit: commit() returns that error until rollback(). A savepoint whose block failed is rolled back with its errors, and the transaction can commit again.
    • Cancelling an ORM future half-way (dropping it, a select! branch losing, a timeout) also poisons the transaction: every later call fails until rollback().

    Constraints

    Section titled “Constraints”

    Constraints run as superuser, once per create/write call on the whole recordset, and after a stored computed field they name is recomputed. In-memory records (new_record) never run them.

    Relational fields

    Section titled “Relational fields”
    • Declare relational fields with Many2one<C> / X2many<C> to carry the comodel in the type: shelf.related(&mut tx, Shelf::BOOK_IDS) then returns a RecordSet<Book>, and vals.commands(Shelf::BOOK_IDS, [Cmd::create(Vals::<Book>::new().set(Book::TITLE, "x"))]) only accepts Book values (anything else does not compile). Option<RecId> / Vec<RecId> remain available, with untyped Commands. On the dynamic surface records.related(&mut tx, "book_ids") returns a Records, records.assign(&mut tx, "shelf_id", &shelf) writes one, and read returns many2one values as [id, display_name] (read_with(.., Load::Raw) gives the bare id); a written many2one list must be exactly [id, name or False].

A plain id list written to an x2many field means set. Commands in a create run after the record exists; updates, unlinks and links are batched per record, many2many pairs of a batch are written in one statement.
    • Fail-loud ownership (ADR 0014 F3): update, delete and unlink on a one2many only accept the record’s own lines (a Validation error otherwise; Odoo would modify any record).
    • One2many full-delete guard (SPEC-REL-050): on a one2many, once a CREATE or LINK was seen in the command list (and always in create), CLEAR is ignored and SET only links, so lines created or linked in the same list are never wiped. Many2many commands have no such guard.
    • New records in memory: New (in-memory) records named by link/set on a database record are created (or, with an origin, linked and updated), so order.assign(&mut tx, "line_ids", &lines_with_new_ones) saves them. Commands on new records only change the cache (see below). Commands on a non-stored x2many apply to its current value in the cache; its inverse method then saves it.
    • A one2many may also be the inverse of a many2one_reference (res_model + res_id): only the rows naming the owner’s model belong to it, and lines created through it get the model name. An integer inverse is refused when the registry is built.
    • A reference value must name a model the field declares and a record that exists (a Missing error otherwise; Odoo stores an empty value).
    • Ids of a multi-row create ascend in input order. When all rows give the same fields (the usual case), each batch of rows is one INSERT … RETURNING; rows giving different fields first reserve their ids (one extra statement).
    • ondelete of a many2one is set null by default (cascade/restrict available; a required field must say which). unlink deletes cascaded rows in the database and only forgets cached values that point at the deleted records; other cached values stay valid. Stored computed fields depending on a many2one that a deletion empties, or on a one2many/many2many that loses records, are recomputed.
    • An error raised by create, write or unlink after it changed data (rows inserted, parents written, lines created) makes commit() refuse until you roll back or the savepoint it ran in is rolled back.
    • inherits = [("library.item", "item_id")] gives the model every field of library.item: creating a record creates its parent, writing a delegated field writes the parent, and the child’s constraints on delegated fields are checked after the parent is written.
    • With check_company_auto, create and write check the check_company fields: their targets must belong to no company or to the record’s company, else a user error lists the conflicts.
    • Differences from Odoo in the SQL (the rows are the same): a negated condition on a many2one path (partner_id.name != 'x') compiles to NOT EXISTS (…) instead of IS NULL OR … NOT IN (…), and without a parent store child_of/parent_of become a recursive sub-query of the same statement (id IN (WITH RECURSIVE …)) instead of one query per level.

    Hierarchies: parent store

    Section titled “Hierarchies: parent store”
    • parent_store = true needs a many2one to the model itself (parent_name, default parent_id) and an indexed parent_path char field; otherwise the registry does not build.
    • The ORM keeps parent_path ("1/4/9/", the ids from the root) up to date in SQL, at once: one extra statement after create, one per new parent when records move. Values given for parent_path are ignored. Moving a record under itself or one of its descendants is a UserError, raised before anything is written.
    • child_of and parent_of on the parent field use the paths (parent_path =like '1/4/%'), in SQL and in memory.
    • Adding parent_store to a model whose table has rows fills every path at the next schema update.

    In-memory records and savepoints

    Section titled “In-memory records and savepoints”
    • model.new_record(&mut tx, vals).await and model.new_with(&mut tx, vals, origin, reference).await build records that are never written; their computed fields compute on read, stored fields come from the origin, other fields from their defaults.
    • A new record’s x2many holds new records: with an origin, the origin’s lines as new records of those origins (line.new_with(.., origin = line) is the same record), so the value’s origin() is the origin’s value; a many2one may point at a database record or at a new record. Reading these for several new records reads the origins once.
    • x2many commands on new records only change the cache: create makes a new line, update changes a line’s values, delete/unlink drop the line from the value (nothing is deleted), link/set add database records as new records of those origins. The lines’ inverse fields follow (a one2many line’s many2one points at the new record). Database records never see new records in their cached values.
    • record.x2many_commands(&mut tx, "line_ids") turns a value back into commands for a database record (Odoo’s convert_to_write): set of the database lines (origins included), then create for each new line without origin and update with the changed values for each new line that differs from its origin; the inverse field is left out.
    • tx.savepoint(async |tx| { … }).await flushes, runs the block in a database savepoint and releases it; when the block fails, the database rolls back to the savepoint and the transaction’s cache is emptied, so later reads see the database again.

    Grouped reads

    Section titled “Grouped reads”
    • Group-by specs: a field, date_field:granularity (hour, day, week, month, quarter, year, or a number part: year_number, quarter_number, month_number, iso_week_number, day_of_year, day_of_month, day_of_week, hour_number, minute_number, second_number), or a many2one path partner_id.country_id[:granularity]. Aggregates: __count, field:sum|avg|min|max|count|count_distinct|bool_and|bool_or|array_agg| array_agg_distinct|recordset. having takes domain-like items over aggregate specs.
    • Group count and pagination: ReadGroup::new(domain).limit(10).offset(20).count_groups(true) also counts all groups, before limit/offset, in the same SQL statement (COUNT(*) OVER ()); groups.group_count() then returns Some(total).
    • Group values: groups.rows() returns rows of GroupValue cells: Null (a NULL item of an array_agg list), False (an empty group value, or an aggregate without values), Bool, Int, Float, Decimal (exact, for numeric columns and their sums), Str, Date, DateTime, Json, Records (a relational group value: one record or empty; also a recordset aggregate) and List (an array_agg list).
    • Datetimes are bucketed in the context timezone (tz); weeks start on Sunday until languages arrive (M3). Selection groups follow the declaration order; a boolean groups NULL with False. Without an order, groups are sorted by the group-by values (many2one by id); with an explicit order, a many2one term follows the comodel’s own order.
    • Everything is one SQL statement, the search predicate included: record rules restrict the grouped rows, the many2many relation joined for a many2many group-by, and a many2one path’s comodel (hidden targets fall into the empty group). Pending writes of the fields involved are flushed first; a domain known to be empty runs nothing.
    • _read_group and _read_grouping_sets are overridable (#[method(override)] async fn _read_group(this, tx, args: ReadGroup, sup: Super) -> Result<Groups>); every caller, the web client’s included, goes through them. read_group is final and returns ids instead of recordsets.
    • _read_grouping_sets(ReadGroupingSets::new(domain, [vec!["a", "b"], vec!["a"], vec![]])) computes several groupings in one statement (GROUPING SETS).
    • numeric sums stay exact decimals; sum_currency needs currency rates and is refused until M3.

    The web client’s methods

    Section titled “The web client’s methods”

    The always-installed web addon puts the web client’s model methods on base: web_read, web_search_read, web_name_search, web_save, web_save_multi, web_resequence, web_unlink, formatted_read_group, formatted_read_grouping_sets, web_read_group, read_progress_bar, search_panel_select_range, search_panel_select_multi_range, onchange and onchange_batch. They take Odoo’s arguments (a specification {field: {fields, context, limit, order}} instead of a field list) and return Odoo’s shapes. Override them per model like any method:

    • records.web_call(&mut tx, "web_search_read", &kwargs) runs a method with keyword arguments given as dynamic values (the JSON-2 body): unknown or malformed arguments, unknown fields in a specification and lossy values are Validation errors (422).
    • web_read_group reads the records of every opened group in one statement and takes the length of a limited level from the grouped statement itself: a kanban with ten open columns costs a few statements, not one per column. web_save_multi writes records sharing the same values together, and per-record values are flushed in one UPDATE per field set.
    • web_unlink raises a UserError with Odoo’s UnlinkBlockedError context (Error::context()) when a restrict reference blocks the deletion, directly or through a cascade; nothing is deleted and no table or constraint name reaches the client.
    • Ordering grouped lists by a numeric field orders by its sum (Odoo’s default aggregator).
    • search_panel_select_range and search_panel_select_multi_range compute range and filter categories/tags for the web search panel, supporting hierarchical categories, counter badges via grouped counts, and custom domains. Omit limit, or send false or 0, for an unlimited display range. A positive limit reaching the display boundary returns {"error_msg": "Too many items to display."}; counters remain complete. Hierarchical category reads apply the limit to comodel records before retaining only closed parent chains. Use hierarchize=false for a flat category list; comodel_domain restricts visible choices. Selection filters ignore group_by and return no group keys. For many2many filters, group_domain is a map from JSON-encoded group IDs to domains: integer ID 7 uses key "7", an unset group uses "false", and a string group ID uses its full JSON string encoding (including quotes and escapes). Keys are parsed as JSON scalars and canonicalized: escaped Unicode and literal UTF-8 keys for the same group ID are equivalent. Missing entries and {} add no restriction; malformed maps, keys or domains raise typed validation errors. For many2one filters, group_domain is instead a domain applied to counters. Relational group_by accepts many2one, selection and other valid scalar fields; compound and binary group values raise an explicit typed error. Counter execution uses one grouped statement per field, including custom per-group predicates; it does not count each choice separately. The returned values use Value::Rows internally, with a shared column layout, while JSON callers still receive an array of choice objects. Relational choices are filtered through comodel search_with and read with read_rows, preserving comodel visibility and display labels.
    • Not yet: group_expand and fill_temporal (M4), other field aggregators (M4), pending attachments in web_save (M3).

    Onchange methods

    Section titled “Onchange methods”
    • An #[onchange] method runs on the in-memory record of the form when one of its fields changes; it assigns fields with set/write and may return values and a warning. The whole onchange is isolated (ADR 0017 §2): nothing it writes, even to database records, persists, and the transaction’s cache is left as it was before the call. An onchange that only reads costs no extra statement; the first statement that would change data opens a savepoint that is always rolled back. A database error on a read inside an onchange aborts the transaction like anywhere else (roll back). A SELECT that calls a function which writes is not recognised as a change: do not call such functions from an onchange. Methods of every addon run in method-name order, each at most once per pass; passes repeat while fields of the form keep changing (unless the context sets recursive_onchanges to false).
    • The record starts from the edited record’s values (computed ones included), so only the dependents of what changed are recomputed. The response contains only what differs from the form, x2many fields as command lists.
    • Return values and warnings:
      • OnchangeResult::none(): nothing besides the assignments made with set/write.
      • OnchangeResult::warning(title, message): a warning the client shows in a dialog.
      • OnchangeWarning::with_options(class_name, sticky) validates optional notification presentation (ADR 0123). Class text is at most 512 UTF-8 bytes, eight distinct CSS identifier tokens of at most 64 bytes, separated only by ASCII spaces. Tokens match [A-Za-z_][A-Za-z0-9_-]*; malformed/duplicate values return Validation. The wire spelling is className; sticky is optional boolean. A single warning preserves these options, including explicit empty class text or sticky false. Complete normalized warnings deduplicate; several distinct warnings combine in method order into the existing dialog, without notification-only options. The default dialog ignores notification presentation.
      • .value(field, value): also assign field (Odoo’s {'value': …}). id is ignored; a name that is not a field of the model is a Programming error (Odoo ignores it).
    • Calling onchange: the web client calls records.web_call(&mut tx, "onchange", &kwargs); Rust code can call records.onchange(&mut tx, values, field_names, spec) directly.

    Onchange on delegated (_inherits) fields

    Section titled “Onchange on delegated (_inherits) fields”
    • Delegated fields work in onchange like the model’s own: the in-memory record gets an in-memory parent (the edited record’s parent, or a new one), the form’s values and first-call defaults of delegated fields go to it, and the parent’s computed fields follow. A payment form changing amount gets the move’s recomputed total back, unsaved amount included; changing a field the move’s computed fields depend on returns those fields too. An onchange method may assign a delegated field (set_value above): it is written on the in-memory parent only.
    • In a one2many whose inverse is the delegate (payment_ids of a move), a line’s delegated values go to the form’s record. Every in-memory line of a one2many points at the form’s record (as in Odoo), so a line’s computed fields see the form’s values; a line or record moved to another parent leaves the old one, so the old parent’s aggregates no longer count it. The cost does not grow with the number of lines: their parents are read together.
    • A delegate pointing at a record that does not exist, or that the user may not read, is a Missing / Access error. A many2one value given as a map is read as the record its id names (its other keys are not applied); without id it is a Validation error (Odoo builds an in-memory record from the map; see docs/design/m1-onchg.md).
    • Outside onchange, a new record takes values of delegated fields only when its delegate is a new record: new with delegated values, or a write on a new record whose delegate is empty or a database record, is a Programming error (Odoo writes them on a new parent). So is a write of delegated values on database records that sets a new record as delegate, or that empties the delegate.
    • Not yet: change_default with ir.default (M3).

    Many2many lines in onchange

    Section titled “Many2many lines in onchange”
    • Every line of a many2many in a form lists the form’s in-memory record in the comodel’s mirror many2many (the field on the same table with the columns swapped), as in Odoo: a tag created in a post’s form has post_count 1, and a computed field of the post over tag_ids.post_ids counts the post on every tag. An edited post is listed once on the tags it already has. It costs no statement per line.
    • Tags linked from the database keep the stored values of the fields the form shows for them (Odoo copies them before building the form’s record), so a post_count in the tag list shows the stored count for them; their mirror lists the post all the same.
    • A tag the form removes still lists the post in its mirror until the onchange ends (as in Odoo; it is not part of the response). Nothing outlives the onchange.
    • A delegated many2many (_inherits) lists the form’s in-memory parent on its lines the same way, also for changed values, where Odoo lists it only on lines whose mirror was already read (docs/design/m1-onchg-m2m.md, candidate divergence D6 of the GRP spec).

    x2many values inside lines

    Section titled “x2many values inside lines”
    • The values of a line command may hold the line’s own x2many values, command lists again, at any depth: [0, "virtual_7", {"tax_ids": [[4, 3, 0]]}]. They apply like the form’s own values, on the line’s current value (a saved line starts from its stored lines, a new line from none); the new lines of a one2many inside a line point at that in-memory line, so computed fields over any level (an order total over the lines’ sub-lines) see them.
    • With the lines’ x2many fields in the specification ({"line_ids": {"fields": {"tax_ids": {"fields": {"name": {}}}}}}), their changes come back as nested command lists inside the line’s command: the method above returns [1, line, {"tax_ids": [[4, tax, {"id": tax, "name": …}]]}] for every line. A saved line linked into the form (LINK) comes back with its stored values and an UPDATE whose nested commands compare its lines with the stored ones.
    • A line’s value of a delegated x2many field goes to the line’s in-memory parent, like its other delegated values.
    • Limits: command lists nested deeper than 16 levels, or more than 100,000 line commands in one call (all levels together, a SET counting its ids), are Validation errors.

    Named caches across processes

    Section titled “Named caches across processes”

    A named cache (tx.ormcache(name, key, compute), tx.invalidate_ormcache(name)) is shared by the transactions of one process. When the server runs with cross-process signals (set up by the server, not by addons), an invalidation is also seen by every other process serving the database:

    • Committing a transaction that called invalidate_ormcache(name) records a change of cache:<name> in the same transaction. Other processes clear that cache before their next transaction runs; no notification is sent for caches, the start of every transaction reads the change.
    • A value your method computes is published at commit only if no other process invalidated the cache after your transaction started. Otherwise it is dropped (it may come from data that is already out of date) and the next call computes it again. Nothing to do in addon code: compute from the transaction you are given.
    • Cache names are 1 to 64 characters of [a-z0-9_.]; committing an invalidation of a cache with any other name fails with a Programming error.

    Partitioned leaf models

    Section titled “Partitioned leaf models”

    Append-mostly tables (an outbox, an audit trail, job history, logs) grow by millions of rows a day and are cleaned up by age. Declare them partitioned: the rows live in one table per hour, day, week or month, the ORM creates the coming partitions ahead of time, and old rows go away by dropping whole partitions (constant time, no DELETE, no vacuum debt). Odoo has no partitioning; the rules below are ERPForAll’s (ADR 0040 D6, docs/design/m3-ormx.md §7).

    partition(...) takes interval ("hour", "day", "week" from Monday, or "month", all in UTC), premake (intervals created after the current one, 1 to 1000; at least 2 for "hour", because partition upkeep may run up to one hour apart), retain (intervals kept before the current one, 1 to 1000, or "all") and, optionally, by. None of them has a default.

    The partition key is always server time. It is create_date unless by names another field, which must be a stored, required datetime field declared server_set. The ORM fills a server_set field at insert with the transaction timestamp, exactly as it fills create_date; the field is readonly in fields_get, never copied, and a value for it in create, write or a data file fails with Programming 'audit.entry.recorded_at' is set by the server and cannot be written. The same error answers a value for create_date on a partitioned model (Odoo drops it silently on other models and still does for write_date; a partitioned model refuses it, whichever column is its key). So no caller can steer a row into a partition, and a row never moves between partitions. server_set is allowed on any stored datetime field without a compute, related path or default, partitioned model or not.

    Only leaf models can be partitioned. The table’s primary key is (id, key): id alone is not unique across partitions, so nothing may reference the model. The registry refuses, when it is built:

    • a many2one (an _inherits delegate is one) or a many2many pointing to the model, and a many2many on the model itself: model 'audit.event' is partitioned, so no field may reference it; 'sale.order.event_id' does;
    • partition on an #[extend]: only the declaration that creates the model decides (partitioning of 'audit.event' can only be declared by its owner (audit_trail)), and a model inheriting a partitioned one under a new name is not partitioned;
    • the access engine’s policy tables (ir.access, res.groups, res.users, …: ADR 0035 D4), abstract and transient models, a fill factor, a table name longer than 51 bytes (partition names append _p and up to 10 digits), and a key that is not server time;
    • partition in models/*.toml: partitioning is declared by native addons only;
    • a business key (keys = [key(...)], the arbiter of upsert): a unique constraint of a partitioned table must contain the partition key, which the server sets on every insert, so no row could ever match it (business key '_k' of partitioned model 'audit.event' cannot be an upsert key: ...; rows of a partitioned model are inserted with create, not upserted), and upsert on a partitioned model is a Programming error too;
    • an exclusion or a WITHOUT OVERLAPS key that does not compare the partition key with = (exclusion '_no_overlap' of partitioned model 'audit.slot' must include the partition key 'recorded_at'): list it in equal (or the key’s fields).

    Soft references (res_model/res_id, reference fields) and a one2many listing the model’s rows from another model are fine.

    Schema sync creates the table PARTITION BY RANGE (<key>) with the partitions of the declared window, named <table>_p<YYYYMMDDHH> (hour), <table>_p<YYYYMMDD> (day, week) or <table>_p<YYYYMM> (month), each covering [start, next start). There is never a default partition. An existing partitioned table that matches the declaration (range on the key, a timestamp key column, primary key (id, key), every partition named and bounded for the interval, no default partition) is adopted as it is, whoever created it: a module that wrote its own partition DDL in this convention moves to the declaration without a rewrite. A table whose partitioning would change (regular to partitioned, back, or a different interval) is created again when it was never written, and refused when it has rows: table 'audit_event' has rows; changing its partitioning is not supported (ADR 0040 D6; business tables: M5 partitioning ADR).

    Upkeep keeps the window. Until the job scheduler runs it for you, call it yourself, from a loop that runs once per interval for example; each call runs on the owner pool (the request role has no DDL right), outside any request transaction:

    • ensure_partitions first finishes any detach an interruption left pending, then creates every missing partition of the window; it is safe to call from several processes at once (a partition created meanwhile is reported existed). retire_partitions marks each old partition, detaches it with DETACH PARTITION … CONCURRENTLY and drops it; a table an interrupted retirement left behind is dropped by the next call. maintain_partitions(owner, now) does both for every partitioned model.
    • The native server calls generic upkeep at startup and periodically with the current installed registry and an owner pool. Addons only declare their partition policy; they do not register an upkeep job. base.partition_upkeep_interval_secs is a database-wide Technical parameter (default 3600 seconds, allowed 60 through 3600). Closed audit/outbox event-table upkeep is separate. This timer is independent of ordinary queue enablement; queue-based execution history for it is not available yet.
    • The returned PartitionReport lists every partition created, existed, finalized, detached, dropped or failed with the database’s reason; a failed step never stops the others, and nothing is skipped silently. It is #[must_use]: check is_complete() or call into_result().
    • Every lock wait of the upkeep is bounded by OrmConfig::partition_lock_timeout (5 s by default, 100 ms to 1 h); a concurrent detach that waits longer for older transactions gives up and leaves the partition pending, and the next call finishes it.
    • Removing a retired partition takes ACCESS EXCLUSIVE on the tables its foreign keys point to (the create_uid and write_uid keys point to res_users), and readers of those tables queue behind a waiting removal. The removal therefore gives up after 300 ms (PARTITION_SHORT_LOCK_TIMEOUT, not the longer partition_lock_timeout): the table stays detached and marked, the report lists it as drop deferred (drops_deferred(), not a failure; also logged as a tracing warning) and the next retire_partitions or maintain_partitions removes it. Attaching a new partition, detaching a retired one and finishing a pending detach take SHARE ROW EXCLUSIVE on those tables, which queues their writers (a login updating res_users) behind a waiting statement; they run under the same 300 ms. A wait that is cut is a failed entry whose PartitionEntry::is_lock_timeout() is true (SQLSTATE 55P03, error kind Lock): not a fault, the next run repeats it (a cut detach leaves the partition attached, or pending, which the next run finishes; the marker erp:retired is taken back from a partition that stayed attached).
    • The 300 ms bound also cuts the wait of a detach or finalize for older transactions (it is database-wide: any transaction open longer than that, in any session, counts). With a long transaction around, a detach stays pending run after run and old partitions are not retired. Watch partition_health: PartitionWindow::pending_detaches() counts the detaches left pending and oldest_pending_end() gives the end of the oldest such partition’s range; a count above 0 over several runs means look for a long-running or prepared transaction.
    • A failed entry carries its structure, not only text: PartitionEntry::step(), reason(), sqlstate() and error_kind(). A scheduler retries is_lock_timeout() entries quietly and raises the others.
    • ensure_partitions(…, Horizon::Through(t)) with t before the interval holding the current time is a Programming error. A step that finds its lock held by another upkeep fails with a Lock error naming the table.
    • maintain_partitions(owner, now) places the window and the retention cutoff by now, one clock; the database’s clock only guards (a cutoff after it is refused, so a clock running ahead cannot retire live partitions). Pass the database’s time, or your own when it is within an interval of it.
    • A partition whose bounds are not a pair of timestamps cannot be compared with the cutoff: every retirement lists it as failed until someone detaches it by hand.
    • Upkeep bumps no cross-process generation: attaching or detaching a partition changes no result shape, and PostgreSQL re-plans the statements that read the table, in every process.

    When upkeep falls behind, inserts fail loudly instead of landing in a catch-all partition: no partition of 'audit.event' accepts create_date = 2026-10-19 10:00:00.123456: partition upkeep has not created it yet (window: 7 days; see the health check) (Database, SQLSTATE 23514). Orm::partition_health(pool) reports, per partitioned model, how many consecutive intervals from the current one have a partition; fewer than 2 is short. It also counts the partitions it cannot place in time (PartitionWindow::unreadable_bounds(): a MINVALUE, MAXVALUE or infinity bound, a default partition); anything above 0 wants a look. A model whose table is missing or not partitioned in the database is a Database error, not a window of 0.

    A partitioned table that already holds rows follows the large-table rule of schema sync (SchemaSyncOptions::large_table_rows). PostgreSQL refuses CREATE INDEX CONCURRENTLY on a partitioned parent, so an index on a large partitioned table becomes one SchemaStep (SchemaStepKind::CreatePartitionedIndex): CREATE INDEX ... ON ONLY the parent (a catalog entry, invalid for now), one CREATE INDEX CONCURRENTLY per partition, and ALTER INDEX ... ATTACH PARTITION, after which the parent index is valid. A step that stopped half-way continues with the partitions that have no index attached yet (a parent index left by another declaration, or without a comment to tell, is dropped with the partition indexes attached to it and built again). Each partition’s build holds the table’s partition upkeep lock, so a retirement cannot detach it meanwhile; a run that cannot take the lock within the step’s lock timeout fails with a Lock error and resumes at the next sync. A UNIQUE or PRIMARY KEY constraint object has no online form (ADD CONSTRAINT ... USING INDEX is refused on a partitioned table), so the install fails before any DDL naming the constraint, the table and the threshold; declare a unique index (it must include the key) instead. An exclusion is refused like on any large table.

    Reads and writes need nothing special: create, read, search, write and unlink work as on any model, with the same statement counts (a read by id probes each partition’s primary key index; the retention keeps their number bounded).

    Search-panel many2many group_domain maps accept at most 64 entries per call; larger maps fail with Validation. This input-shape bound does not limit returned choices or truncate counters.

    A native selection_method uses #[selection] inside #[methods]. Its second parameter is &mut SelectionContext, and it returns Result<()>. Emit each pair through the checked sink, or read an authorized stored-text catalog:

Ordinary #[method] signatures are refused before execution. Provider names can remain owned registry strings; no 'static conversion is needed.

    emit checks duplicate keys and admission before copying. One metadata operation, including sibling fields and ctx.resolve(model, field) re-entry, shares at most 4096 pairs, 1 MiB owned UTF-8 key/label bytes, depth 16 and 8192 work units. Limits are positive and can only tighten. Pair emission, catalog rows, provider entries, catalog domain/value nodes (including policy predicates) and explicit ctx.charge(work) each consume work. Charge native calculations before performing them or copying their results. A caught failure still refuses the outer metadata operation. Empty catalogs are valid; duplicate keys and NULL keys or labels are errors. Static selections and callable field-value conversion keep their existing behavior: a callable catalog is not a generic membership constraint.

    catalog retains the caller’s model/field/record rights, company and active context, and database snapshot. It supports stored text projections and direct stored scalar domains/orders with literal or principal-parameter operands. Custom nodes, opaque SQL/query operands and nested domain values refuse before optimization. Relational traversal, hierarchy/access operators and nonstored projection fields refuse; they do not trigger arbitrary computed callbacks. Pending writes are prepared before capability entry. SQL limits candidates and suppresses oversized strings before the driver receives them. There is no cross-transaction catalog cache.

    The capability exposes environment inspection, emit, catalog, resolve and charge. It exposes no mutable transaction, raw SQL, create/write/unlink, flush, commit-hook registration or transaction control. Native Rust is trusted executable code: cooperative charging does not sandbox arbitrary CPU, allocation, files or network access. Untrusted executable providers require a separate script/Wasm budget; #[selection] is currently native-only.

    Outbox checkpoint limitations during schema upgrade

    Section titled “Outbox checkpoint limitations during schema upgrade”

    Stored-compute backfills that can change eventful physical fields are not supported yet. Schema planning refuses them before applying planned DDL or backfill writes, including a non-eventful source whose computed dependencies reach an eventful model. A previously queued backfill is checked against the current registry on resume. The error says that capture of the stored-compute backfill is not available yet. No request identity is substituted for a system upgrade origin. Keep affected addons from opting into events until this system-origin boundary and the lead’s other pre-opt-in follow-ups are delivered. Fresh creation of a table without a backfill is separate. An existing table that holds no row is admitted: the new column is added, nothing is backfilled and no event is written, because there is no record to report. A table whose rows were deleted but not yet vacuumed away is still refused, because the check after the column is added looks at the table’s physical size; a VACUUM of the table normally gives those pages back (it skips that step when it cannot take the lock), after which the sync is admitted.

    An eventful model may have at most 128 fields with a column of its own table (id not counted), because one event lists at most 128 changed field names. A model above that limit, including one an extension makes eventful or one a custom field pushes over it, is refused when the registry is built, with an error naming the model, the addon that opted it in, the count and the limit. Whether wide models such as journal entries get a larger bound is an open lead decision.

    Frozen ABI1 generic guest create/write calls are subject to the same native-field refusal as direct guest CRUD, even when the called model has only native methods. Host/RPC calls to entirely native chains still accept the native scalar types. When a WASM override is present in a create/write chain, explicit native-field writes are refused for every caller before native hooks or lossy argument conversion. Ordinary neighboring fields remain usable; no whole-model activation ban applies.

    See also: Tracked fields (tracking = true | <sequence> and the change capture).

    Read-audit model declarations

    Section titled “Read-audit model declarations”

    audit_reads = true selects successful RPC reads of the invoked model for independent auditing (ADR 0167 D4). Use it on native models or extensions, ModelDecl::audit_reads(true), ModelDef::audit_reads(true), data-only model TOML, or described WASM model arguments. The default is false. Composition ORs every declaration in the model’s MRO: a false extension cannot disable a true declaration. Abstract mixins contribute to concrete descendants, and transient models may opt in. Delegation alone does not transfer the flag. A registry rebuild recomputes it from the currently loaded declarations.

    A selected read remains READ ONLY. Its result is buffered until an independent read_ok attempt commits; audit failure withholds the result with erp.audit_unavailable and does not rerun the successful method. Operator policy can widen selection, and request context cannot disable it. This flag does not grant read access or admit additional principal kinds to RPC.

    Column collation

    Section titled “Column collation”

    A stored Char or Text field can select byte ordering explicitly:

    The closed choices are "C" and "default". Omission inherits an earlier declaration; otherwise it uses the database default. An extending addon can select collation = "default" to reset an inherited C. Native FieldDecl::collation and owned FieldDef::collation use the same names; data-only model fields accept a string collation property. Unknown names and nontext, translated, company-dependent or nonstored storage are refused at registration. Locale and ICU collations are not available.

    C compares bytes in the database encoding. In UTF-8 this agrees with code-point ordering, not natural-language order. It does not normalize Unicode or make equality case-insensitive. PostgreSQL case conversion and character classification also use collation; selecting C is not a promise of Unicode case folding. Ordinary column indexes inherit the column’s collation.

    Schema sync compares catalog identities, including when the database itself defaults to C. Changing an ordinary stored column’s choice runs transactional DDL and can rebuild indexes; use a maintenance window when the normal schema admission requires one. It preserves existing varchar width when a narrower declaration would otherwise be ignored. Dependent database objects can refuse an alteration, and the operation must then roll back. Existing generated outputs require explicit migration for collation changes; fresh outputs support the declaration. A view’s explicitly declared output collation must match its installed output. Only the owning addon and admitted co-owners can change a protected stored field’s collation.

    For an existing generated output without an explicit collation declaration, its recorded installed provenance remains authoritative, including a trusted owner migration. An explicit declaration is checked against that identity before automatic sync; catalog-only drift still refuses.
