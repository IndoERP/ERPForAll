    Ledger configuration models of the account addon

    Source: addons/account/src/ledger/ (accounts) and addons/account/src/journal/ (journals). Spec: docs/specs/accounting/ledger-config.md (ACCLED). Plain company accounting configuration lives in addons/account/src/company/.

    The models

    Section titled “The models”
    ModelTableWhat it is
    account.accountaccount_accountAn account of the chart. Shared by the companies of company_ids.
    account.account.tagaccount_account_tagA reporting tag (accounts, taxes, products). Unique per name, applicability and country.
    account.rootaccount_rootThe first two characters of a code, as a small tree (10 below 1).
    account.code.mappingaccount_account_codeThe code of an account in one root company.

    Codes live in a table

    Section titled “Codes live in a table”

    Odoo keeps the code in a company-dependent JSON column and checks uniqueness with a Python search. Here the code is a row of account_account_code per account and root company (ADR 0048 D3):

    • UNIQUE (company_id, code): two accounts of one company tree cannot share a code, and the database says so (SPEC-ACCLED-017, Parity: divergent, ADR 0048 D3). Sibling company trees have different roots and may reuse a code.
    • UNIQUE (account_id, company_id): one code per account and tree.
    • A branch company reads and writes its root’s code (SPEC-ACCLED-029, 030). A mapping row for a branch is refused.

    account.account.code is a computed, writable field over that table in the environment’s company (depends_context = ["company"]). Writing it stores the code for the root of the active company, or removes the row when the value is empty. account.root rows are created when a code is stored and never removed; each missing prefix is one insert-if-absent on the _name_uniq key (the ORM upsert with nothing to update), so two transactions that first use the same prefix both succeed (the later one is retried by Orm::run after a serialization failure).

    A code given at create is stored for the root of the active company when the account belongs to that tree, else for the root of the account’s first company that is also a company of the caller (lowest company id), as the reference creates under the caller’s allowed companies (odoo/addons/account/models/account_account.py:1023-1025, :1042-1043). A caller with companies [A, C] creating an account of [B, C] stores the code in C’s tree, never B’s; when the account belongs to none of the caller’s companies the create is a Validation error. Only superuser mode takes the lowest company id of the account. An account created from company A with company_ids = [B] in superuser mode therefore reads its code in B and uses no code of A’s tree. A code value that is neither absent, null nor text is a Validation error. The account_id and company_id of an account.code.mapping row are set at create only; account_id is readonly (the one2many sets it) but company_id is not, so the “Codes by company” list can send it for a new row. A write that gives either a value other than the stored one is a Validation error; naming the stored value passes. Only code is written.

    Reading code without an active company in the context is a Validation error, not an empty value.

    A create may carry code_mapping_ids create commands. The x2many values of a create are written in field order, and the company check of a row reads the account’s company_ids, so code_mapping_ids is declared after company_ids in the model; keep that order in any extension that adds company-checked one2many fields to an account. A row for a company outside company_ids is refused by the company check, never skipped.

    Type rules

    Section titled “Type rules”

    account_type has the 19 types of the reference. internal_group (the part before the first underscore) and include_initial_balance are stored computed fields; reconcile is a stored computed field that the type forces for receivable, payable, bank and cash, credit card, off-balance and the income, expense and equity groups, and leaves to the user for the other asset and liability types. Constraints: receivable and payable must reconcile; off-balance must not and cannot carry default taxes; a bank or cash account has one company; every account has at least one company; a code uses letters, digits, dots and dashes. An account created without company_ids gets the active company.

    Extending

    Section titled “Extending”

    Another addon adds fields with #[extend(AccountAccount, addon = "...")] (or AccountJournal) as for any model (see Extending other addons). The _check_* constraints compose through the usual override chain. The move slice adds the journal item guards.

    The numbering declaration

    Section titled “The numbering declaration”

    The journal stores what the reference reads back from the previous entry name (ADR 0048 D2.2): sequence_reset (never, year, month, year_range, year_range_month), sequence_padding (1 to 64 digits), refund_sequence and payment_sequence. They default from the type (sales and liquidity journals: yearly, five digits; the others: monthly, four digits; credit notes apart for sale and purchase, payments apart for bank, cash and credit card); values given at create are kept. The restart rule and the digits are set only at create: a later type change keeps them, while the two separate-chain flags follow the type. The database refuses digits outside 1 to 64.     A journal whose code and numbering cannot make a valid pattern is refused when it is saved, never at posting. account.sequence.chain.journal_id is still an integer column; it becomes a many2one to account.journal with the journal entry work, which also rewrites the numbering tests that use free journal ids.

    Section titled “Journal settings”

    Declared settings of the accounting app (database scope, block “Journals”; read: account.group_account_readonly, write: account.group_account_manager):

A value of the wrong kind or outside its bounds is refused naming the key and its bounds; an empty list of account types is refused. A changed setting applies to the next create or write of a journal or account: existing journals are not checked again.

    Journal dashboard card

    Section titled “Journal dashboard card”

    account.journal.dashboard_card is a computed, non-stored text field holding the card contract v1 as JSON (buttons, stats, chart; addons/account/src/journal/dashboard.rs). The kanban account.account_journal_dashboard_kanban_view (action account.open_account_journal_dashboard_kanban, menu Accounting > Dashboard) shows it with the dashboard_card widget for the journals with show_on_dashboard. Each card element and its reference counterpart: docs/design/accounting-dashboard-matrix.md.

    • One computation serves every requested journal with a fixed set of grouped reads (_read_group on account.move and account.move.line), never one query per journal; the reads run with the reader’s rights, so record rules and the company scope apply. A reader without accounting access gets the access error.
    • Every stat and chart is always shown; one that counts nothing shows zero in the neutral tone (the reference hides such a row and draws sample bars on an empty journal).
    • Sales and purchases: button New Invoice or New Bill; “Drafts”, “Unpaid” (sales) or “To pay” (purchases) and “Late” (posted, due before today in the user’s time zone) from the lines on receivable and payable accounts (balance, purchases shown positive, date_maturity); a bar chart of the posted invoiced (billed) amount per month. Each figure opens account.action_move_out_documents (sales) or account.action_move_in_documents (purchases): the invoice list without a document-type domain, so it shows every document the figure counts.
    • Bank, cash and credit card: no button; “Balance”, the posted balance of the default account in the journal’s company, linking to its journal items; “Transactions”, the number of the journal’s plain entries, opening them (until statements exist); a line chart of the running balance per day.
    • Miscellaneous: button New Entry; “Drafts”; no chart.
    • Until reconciliation exists, “open” means posted: the residual replaces the balance when it arrives.
    • Labels are in the source language (dashboard::labels): the addon has no server-side code-text translation yet.
    Setting (database scope, block “Dashboard”)DefaultBounds
    account.dashboard_graph_months13 (the current month and the twelve before)1 to 36 months
    account.dashboard_balance_days307 to 64 days (one chart point per day; a card shows at most 64)

    Journal groups

    Section titled “Journal groups”

    account.journal.group (a “ledger”): name unique in the database (“Another ledger already has this name.”), sequence (default 10) and included_journal_ids, the journals whose journal_group_id points to it, archived ones included. Like the reference it has no company. A ledger that a journal uses, archived journals included, cannot be deleted (journal_group_id is restrict): the reference empties the ledger of the journals of every company.

    Data and security

    Section titled “Data and security”
    • Default data: the three master tags (account_tag_operating, account_tag_financing, account_tag_investing), which cannot be deleted. The reference ships no accounts, roots or code mappings: accounts come from a chart template (the chart-template slice) and roots follow the codes (SPEC-ACCLED-053; tested in crates/erp-cli/tests/account_install.rs). No journals or journal groups either: the reference creates the standard journals when a chart is loaded into a company, and that list belongs to the chart-loading slice (SPEC-ACCLED-102).
    • Groups (security/account_security.xml): group_account_readonly, group_account_user, group_account_manager. the security-data slice extends them.
    • Company rule: generated from company_access (accounts by company_ids and ancestors, code rows and journals by company_id and ancestors). Journal groups have no company.
    • Access: journals and journal groups are read by group_account_readonly and managed by group_account_manager.
    • Menus: Accounting > Configuration > Chart of Accounts, Account Tags, Journals (managers), Ledgers.

    Company accounting configuration

    Section titled “Company accounting configuration”

    The account addon extends res.company with ordinary account references for transfers, bank suspense, cash differences, cash discounts, exchange differences, PoS receivables and accruals, and journal references for exchange differences and automatic entries. References start unset, use restrictive foreign keys and obey the framework’s company consistency rules. An account or journal of an unrelated company cannot be assigned, including through elevated ORM operations; permitted parent-company targets remain usable by a branch. Removing a selected account’s company membership or moving a selected journal is refused when it would strand a configuration reference. The refusal names no hidden company. Failed native writes still require an enclosing savepoint or transaction rollback, as other ORM writes do. These fields are ordinary company columns, independent of the typed company-dependent account mappings.

    Company fields also store bank, cash and transfer account-code prefixes (empty or up to 64 ASCII letters, digits, dots and dashes), tax rounding (round_globally by default or round_per_line), Anglo-Saxon accounting (false by default), and whether a chart is expected (true). Prefix and option writes configure future consumers; they do not create or rename accounts or post entries. The chart identifier is read-only until chart activation is available. The company form cannot activate or clear an installed chart.

    Settings > Accounting > Company accounting opens the explicitly selected company’s configuration form. This is a scoped Settings link, not a second copy of the relational values in scalar settings storage. Existing company-management permissions apply; accounting-manager membership alone grants no company writes. Configuration writes check company scope before reading target details. Existing fiscal-year settings and lock-date policy remain separate; the form does not offer a generic lock-date editor.

    Installation and upgrade

    Section titled “Installation and upgrade”

    Upgrade account before serving a binary that declares the company configuration link: the upgrade installs its action and form along with the new columns. A missing link target is refused during Settings publication. Existing companies retain their tax, lock and accounting configuration on upgrade. No jurisdiction-specific accounts or journals are seeded by this extension; references remain empty until configured from the company’s chart.

    Not available yet: automatic journal account creation, use of company suspense/cash-difference defaults by journals, prefix-driven renumbering, chart activation, and effective company-dependent receivable/payable/income/ expense/valuation defaults. These limitations are independent of saving the plain configuration fields.

    A condition on code (=, !=, in, not in, like, ilike, =like, =ilike and their negations, = False) matches the code of the active company’s tree, as reading the code does: a branch searches its root’s codes, and an account shared by two trees is found by the code of each tree in that tree. A name search (a many2one field) matches the name or the code as contained text; the reference matches the code by prefix. Internal users read account.code.mapping, so such a search works for anyone who may read accounts.

    Account tax choices

    Section titled “Account tax choices”

    tax_ids holds default taxes and enforces the account’s company applicability. A tax distribution’s account_id restricts account deletion, including hidden/archived owners. The model-level refusal checks unlink authority first and gives no unreadable account labels. Archiving is supported; there is no deprecated field. See Tax definitions for company/product defaults.
