    AI providers and tool calling

    The core framework has no HTTP client for AI and never needs a model to run. A provider (a hosted service or a local server) is an addon that implements the traits of erp_sdk::ai:

    • ModelProvider: text completion, streaming and token counting with CompletionRequest and CompletionResponse. Every completion and embedding call reports a UsageRecord (tokens, cost, latency).
    • EmbeddingProvider: vector embeddings.
    • ToolModelProvider: tool turns, on top of ModelProvider. A provider that cannot call tools does not implement it, so code that needs tool calling does not compile against it.

    Design: docs/design/m3-ai0-iface.md (text and embeddings) and docs/design/ai1-sdk-tools.md (tool calling); decision record ADR 0188.

    Tool turns

    Section titled “Tool turns”

    A tool turn is a ToolTurnRequest: a model name, the conversation as TurnMessages and the ToolSpecs the model may call. Each message is a role (TurnRole::System, User, Assistant) and a list of ContentParts:

    PartWho sends itWhat it is
    Instructionsystemtext built from &'static str pieces and typed values
    UserTextuserwhat the user typed
    Data (LabelledData)user sidea value a tool read, labelled with its DataSource (tool, model, record ids)
    ToolResultuser sidethe answer to one tool call, tied to it by id, holding LabelledData
    ToolCallassistanta call as the model produced it: id, name and arguments, kept as received
    AssistantTextassistantthe model’s own prose, resent with the history (any String)

    TurnMessage::new refuses a part its role may not carry and an empty message. ToolTurnRequest::new refuses two tools with one name, a repeated tool call id, a tool result for a call no earlier assistant message made, and a second result for one call. A provider answer is a ToolTurnResponse with assistant parts only, and finish_reason is FinishReason::ToolUse when the model waits for tool results.

    Instruction has no conversion from a runtime String, no parsing, no deserialization and no default; LabelledData has none from any string, and its only constructor is LabelledData::new(source, value). Compile-fail cases and a compile-time probe pin this (SPEC-AIA-001, partial). The types do not close every path. Three are review rules for ai_base:

    • A leaked String (String::leak) is a &'static str and passes Instruction::from_static. Only string literals go there.
    • Any crate can call LabelledData::new. Only the tool executor builds it.
    • ContentPart::AssistantText holds any String. Only provider responses supply assistant parts.

    Limits

    Section titled “Limits”
    ValueRule
    ToolName1 to 64 characters from A-Z a-z 0-9 _ - (the common subset of the hosted providers’ rules)
    ToolSpec descriptionnot blank, at most 1,024 characters
    ToolSpec input schemaa JSON object whose top-level "type" is "object"
    ToolCallId1 to 256 bytes, no control or Unicode format (Cf) characters
    ToolCall nameat most 256 bytes; it need not be a valid ToolName, so the executor can answer “unknown tool”
    DataSource modelnot empty when present

    Each refusal is a ToolTypeError variant naming the value or position. An adapter that cannot represent a provider’s answer (an empty id, an oversized name) returns ProviderError::InvalidResponse, never a guessed value.

    Implementing a provider

    Section titled “Implementing a provider”

    Implement ModelProvider first, then ToolModelProvider::complete_turn. Lower each part to the provider’s wire format: Instruction::render() goes in the system slot, LabelledData is serialized as data (never as instruction text), and ToolCall and ToolResult keep their ids. Build the answer with ToolCall::new and ToolTurnResponse::new, and map their errors to ProviderError::InvalidResponse. ToolTurnResponse::new refuses an empty answer, a part a response may not carry and a repeated call id; it does not bound sizes. Byte and depth limits on provider responses (argument size and depth, text length, part count) belong to the adapters. Wire lowering per provider, delimiters around data and streaming of tool turns are planned.

    Testing with the scripted provider

    Section titled “Testing with the scripted provider”

    erp_testkit::ai::ScriptedModelProvider answers each tool turn with the next queued reply and records every request:

    push_error queues a ProviderError. When the script runs out, complete_turn returns ProviderError::Backend naming the call number, never a default answer. Text-only requests (complete, stream, count_tokens) behave like MockModelProvider, which echoes the prompt. The scripted name and arguments are kept as given, so a test can script a call to a tool that does not exist. The round trip is tested in crates/erp-testkit/tests/ai_tools.rs (SPEC-AIA-002).
